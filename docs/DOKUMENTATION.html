1. Was ist das System?

Das Bewerbungs-Management-System (BMS) ist eine lokale Web-App, die die gesamte Jobsuche einer Person an einem Ort bündelt: Stellen finden und bewerten, Firmen prüfen, Bewerbungsunterlagen erzeugen, Interviews vorbereiten und nachbereiten, E-Mail-Antworten tracken, das Netzwerk pflegen und aus allem lernen.

Es ist bewusst kein autonomer Bewerbungs-Roboter, sondern ein Human-in-the-Loop-Werkzeug: Das System findet, bewertet und verwaltet — der Nutzer entscheidet. Kein Versand ohne Freigabe, keine Bewerbung ohne Sichtung, keine erfundenen Fakten.

Die zentrale Idee: Claude-in-the-Loop

Statt externer API-Keys und teurer Dienste ist die „Intelligenz" des Systems Claude selbst. Sogenannte Skills (Suche, Scoring, Firmen-Prüfung, CV-Anpassung, Gmail-Auswertung …) werden per Klartext-Satz ausgelöst und schreiben ihre Ergebnisse in dieselbe zentrale Datenbank, aus der die Web-App liest. Es gibt zwei Betriebsarten:

  • Interaktiv — Der Nutzer sagt in einer Claude-Session z. B. „Firma prüfen für Job <Nr>", Claude führt den Skill aus.
  • Headless — die Web-App startet über den Agent-Runner denselben Skill als Hintergrund-Lauf (claude -p "<Trigger-Satz>"), z. B. per „▶ Ausführen"-Button an der Stelle.

Beide Wege nutzen exakt dieselben Skills und schreiben in dieselbe DB — es gibt keine zweite Wahrheit.

Zwei KI: Claude oder ChatGPT (P2-86)

Die Läufe gehen wahlweise über Claude Code (claude -p, Standard) oder über die Codex CLI von OpenAI (codex exec, ChatGPT, im ersten Release eine Vorschau). Gewählt wird in sucheinstellung.ki_anbieter (claude | chatgpt) über GET/PATCH /api/einstellungen und die Karte „KI“ der Einstellungen; die Installationsanleitungen fragen sie in Schritt 0 ab. GET /api/ki-status meldet je Anbieter, ob das Programm installiert und angemeldet ist, und liest nie einen Schlüssel. Queue, Ketten, Timeout und Abbruch bleiben in agent_runner gemeinsam, app/ki_anbieter.py hält, was sich unterscheidet:

  • Aufruf und Umgebung: codex_argv baut codex exec --json mit Sandbox workspace-write, Netz an und dem Prompt über die Standardeingabe. codex_prompt nennt den Skill ausdrücklich, codex_umgebung entfernt OPENAI_API_KEY, CODEX_API_KEY und die Claude-Variablen: Es gilt die Anmeldung des Rechners (codex login, das Abo), nie ein getrennt abgerechneter Schlüssel. Das Programm findet das BMS über CODEX_BIN oder den PATH.
  • Skills: .claude/skills bleibt die einzige Quelle. skills_spiegeln kopiert sie vor jedem Lauf nach .agents/skills (nicht versioniert), dort sucht Codex. AGENTS.md im Projekt übersetzt die Werkzeugnamen der Skills (WebSearch, WebFetch, Read, Write, Edit, Task), die Skills selbst nennen weiter die von Claude Code.
  • Auswertung: CodexAuswertung macht aus dem JSONL-Strom das Ergebnis, das der Runner von claude -p kennt. Ein erreichtes Abo-Limit und eine fehlende Anmeldung erkennt es am Fehlertext (abo_limit, anmeldung).
  • PDF: LibreOffice bricht in der Sandbox von Codex ab. codex_umgebung setzt deshalb BMS_PDF_UEBER_SERVER, und cv_export lässt den Server außerhalb der Sandbox umwandeln (POST /api/intern/pdf, nur Word-Dateien aus Programm- und Datenordner).
  • Kosten: Codex meldet keine Kosten in Dollar und Token erst am Ende des Turns. Unter ChatGPT bleibt AgentTask.cost_usd 0, der Verbrauch steht in AgentTask.tokens, und es gibt keine Budgetgrenze je Lauf. Schutz sind das Zeitlimit des Laufs, die Grenzen des Abos und die Tagesgrenze für Läufe.
  • Modelle: Gespeichert bleiben die Stufen opus, sonnet, haiku, CODEX_MODELL ordnet ihnen die Codex-Modelle zu (§8 „KI-Modelle“). Fable bleibt nie wählbar.
  • Rechte: Die Hooks und Freigaben aus automation/agent_settings.json und der Pfadwächter gelten nur für Claude Code. Unter ChatGPT begrenzt die Sandbox das Schreiben auf das Projekt, den Log-Ordner (dazu den Datenordner, wenn er außerhalb des Projekts liegt) und bei Mail-Läufen den Ordner der Zugangsdaten. Das Lesen lässt sie im ganzen Benutzerordner zu, auch unter ~/.bewerbung_mgmt_secrets: Ein Lauf muss dorthin nicht, verhindert wird es aber nicht.

Umgebungs-Fallstricke (wichtig)

  • iCloud Drive (nur wenn das Projekt dort liegt): Sandboxed-Prozesse (Claude-Code-Preview-Panel, launchd/cron ohne „Vollständiger Festplattenzugriff") können iCloud nicht lesen. Die App läuft dann nur über Terminal / start.command. Außerhalb von iCloud entfällt die Einschränkung.
  • Frontend-Build in iCloud: Dort NIE npm run build direkt im Projekt — iCloud re-materialisiert node_modules und zerstört Symlinks. Stattdessen frontend/build.sh (baut außerhalb von iCloud unter ~/.bewerbung_mgmt_node/ und kopiert nur dist zurück). Liegt das Projekt nicht in iCloud, genügt npm ci && npm run build in frontend/.
  • venv liegt außerhalb des Projekts unter ~/.bewerbung_mgmt_venv.
  • PDF-Export: LibreOffice headless (soffice --headless --convert-to pdf), nicht Word — deterministisch, kein Fenster, keine Automation-Freigabe.

Projektstruktur und Ablageorte

Der Projektordner trennt den versionierten Code von den persönlichen Inhalten einer Installation. Maßgeblich ist immer .gitignore, nicht der Ordnername.

  • Code, versioniert (Git): backend/ (FastAPI-App, Pipelines, DB-Layer), frontend/ (React/Vite-Quelle), .claude/ (Skills, Slash-Commands, Beirat-Subagenten), docs/ (Anleitung, Systemdoku, Beirat-Charta), assets/ (Report-Theme als CSS-Master, Logo/Icon), scripts/ (Betriebs-Skripte), automation/ (Vorlage agent.env.example, Guardrail-Konfiguration agent_settings.json), .env.example, .gitignore, die Startdateien (start*.command, start_windows.bat, …) und README.md.
  • Persönliche Inhalte, rein lokal (nie in Git): data/ (die SQLite-DB, Backups, Company-Fit-Dashboards, Digests, Transkripte, Beirat-Protokolle, Papierkorb …), outputs/ (generierte CVs und Anschreiben als .docx/.pdf) sowie die persönlichen Dateien in config/ (profil.md, zielfirmen.md, suchprofile.yaml, budgets.yaml). config/ ist gemischt: scoring_rubrik.md (Bewertungsraster, mit einem Beispiel-Zielprofil) und coach_export.yaml sind versioniert, profil_struktur.md erzeugt die App selbst aus der Datenbank (beim Start, wenn sie fehlt, und bei jedem Speichern der Profil-Seite) und versioniert sie nicht, weil sie den Werdegang enthält.
  • Secrets, außerhalb des Projekts: agent.env (Claude-OAuth-, Apify-Token; ChatGPT braucht sie nicht, die Anmeldung liegt bei Codex selbst), die Gmail-Tokens (gmail_credentials.json, gmail_token.json), die Mail-Konto-Einstellungen (mail_settings.json) und die Coach-Site-Konfiguration (coach_settings.json samt Coach-Zugangsdatei coach_htpasswd; die ältere coach_sftp.env bleibt als Rückfallweg liegen) liegen unter ~/.bewerbung_mgmt_secrets/ (Verzeichnis chmod 700, Dateien chmod 600; Override BMS_SECRETS_DIR), nicht unter automation/. Grund: Alles im Projektordner läge sonst bei Ablage in einem Sync-Ordner (z. B. iCloud) auf jedem Gerät desselben Kontos.
  • Task-Logs, außerhalb des Projekts: Der rohe Ausgabestrom jedes Agent-Laufs (Runner-Prozess wie Beirats-Engine) — u. a. gelesene CV-Inhalte und Mail-Volltexte im Klartext — liegt unter ~/.bewerbung_mgmt_logs/ (Verzeichnis chmod 700, Dateien chmod 600; Override BMS_LOG_DIR). AgentTask.log_path ist seither ein BEZEICHNER, kein direkt verwendbarer Pfad; agent_runner.resolve_log_path() löst ihn auf (neuer Ort zuerst, alter projektrelativer Pfad als Fallback).
  • Git-Interna bei iCloud-Ablage: Liegt das Projekt in iCloud Drive, kann das Git-Verzeichnis als .git.nosync/ ausgelagert werden (git init --separate-git-dir; .git im Projektroot ist dann nur eine Zeiger-Datei), weil Git-Interna (Objekte, Refs, Locks) keinen Live-Sync vertragen. Außerhalb von iCloud ist das nicht nötig.

3. Grundprinzipien

Diese Prinzipien ziehen sich durch das ganze System und erklären viele Design-Entscheidungen:

  1. Human-in-the-Loop. Nichts Unumkehrbares passiert ohne Freigabe des Nutzers. E-Mails werden nie gesendet, nur als Gmail-Entwurf angelegt. Keine automatischen Bewerbungen (Phase 15 „Auto-Bewerben" wurde bewusst verworfen).

  2. Anti-Halluzination. Skills mit Rechercheanteil arbeiten belegt und wörtlich. „Liegt nicht vor" statt Raten. Entscheidungen, die das System nicht treffen darf (Termine, Zusagen), werden als [BITTE PRÜFEN: …]-Platzhalter markiert.

  3. Vier-Augen-Prinzip für Job-Treffer. Jeder gefundene Job muss ein Verifikations-Gate passieren, bevor er in die DB darf: Ein mechanischer URL-Prüfer (verify_jobs.py) plus ein separater, adversarialer Prüf-Subagent bestätigen Existenz und Aktualität. Eine bloße Freitext-Warnung im Fundtext schützt nicht — nur ein Gate, das der Ingest erzwingt. Vertrauensmatrix: Apify-/Mail-Alert-/Nejo-URLs gelten als authentisch; WebSearch-konstruierte URLs brauchen eine kanonische Anzeige, sonst werden sie nicht ingestet.

  4. Dedup lebt von behaltenen Rows. „Verworfen → Kein Match“ bleibt als Tombstone in der DB, damit derselbe Treffer (gleicher Link) nicht am nächsten Tag wieder als „Neu“ auftaucht. Gleiche Logik beim Löschen von Stellen (Soft-Delete, Phase 32). Seit P2-36 unterscheidet der Ingest: Dieselbe Anzeige (gleicher Link), jede weitere Anzeige zu einer noch laufenden Stelle und Treffer im Papierkorb bleiben gesperrt. Eine NEUE Anzeige derselben Stelle (Firma + Titel, Gender-Zusatz egal) zu einer Stelle im Endstatus erscheint dagegen wieder als „Neu“, mit Hinweis NEUAUSSCHREIBUNG?. Fall A: Eine Stelle „Head of Customer Success (m/w/d)“ war als Kein Match aussortiert, die neue Anzeige „(m/f/d)“ kam zwei Wochen später und führte zu einer Bewerbung. Eine reine Sperre hätte sie still verworfen. Seit P2-39 wird für den Abgleich zusätzlich der Firmenname bereinigt (Rechtsform-/Regionszusätze wie GmbH/SE/Deutschland/EMEA entfernt), damit zwei Schreibweisen derselben Firma nicht an zwei verschiedenen Firmen-Rows vorbeilaufen (Messung an einem Echtbestand, 12.09.2026: 15 Firmen-Gruppen fallen zusammen, 5 echte Stellen-Paare kommen dadurch neu zusammen, 0 Fehlalarme). Fall B: Zwei Schreibweisen derselben Firma („Beispiel“ und „Beispiel GmbH“) — drei Stellen hingen an zwei Firmen-Rows für denselben Arbeitgeber, jede Dublettenstufe verfehlte den Treffer, bis die Firmen-Schreibweise selbst bereinigt wurde.

  5. Budget-Leitplanken. Echtes Geld (Apify) hat harte Tageslimits ($0,50/Tag, BudgetLimit-Tabelle). Der headless Claude-Runner läuft aufs Max-Abo (virtuelles Geld), hat aber Ausreißer-Bremsen (Pro-Lauf-Deckel, Tasks/Tag). Unter ChatGPT gibt es keine Kosten in Dollar und keinen Deckel je Lauf (Codex meldet Token erst am Ende des Turns), die Bremsen sind Zeitlimit, Abo-Grenze und Tasks/Tag.

  6. Abgeleitete Sichten statt Write-Trigger. Excel-Export, Tages-Digest, Volltext-Suchindex und seit Phase 81 der Coach-Site-Export sind komplett neu baubar (refresh_views.sh bzw. coach_site.sh), nicht an zehn Schreibstellen verteilt. Ihr Baustand ist sichtbar (Staleness wird gezeigt, nicht versteckt). Der Excel-Export selbst bildet inzwischen zusätzlich den 0–100-CV-Match-Score, den Aussortier-Grund (aus „Notizen & Verlauf" statt einer leeren Spalte) und die Beirats-Bewertung als gefärbte Zahl ab (Phase 75). Seit P2-81 zeigt das Blatt „Bewerbungen" je beworbener Stelle Funddatum, Bewerbungsdatum, das Datum jeder Gesprächsrunde 1–6 (interview.scheduled_at, ersatzweise transcript.recorded_at) und das Absagedatum (früheste Absage-Mail, ersatzweise der Statuswechsel im Verlauf, als lokaler Kalendertag).

  7. Ein Aktivitäts-Log für alles. Jede Hintergrund-Aktivität — Runner-Skill wie In-Server-Engine (Beirat) — schreibt ihre AgentTask-Row selbst (Status, Log, Dauer, Kosten). Das Task-Center liest nur diese Tabelle und zeigt damit automatisch ALLES; keine Parallel-Buchführung (Phase 42).

  8. Nur für die bewerbende Person. Das BMS unterstützt ausschließlich die Seite, die sich bewirbt. Funktionen, mit denen Arbeitgeber Bewerbende bewerten, sortieren oder auswählen, kommen nicht hinein: Sie fielen unter die Hochrisiko-Regeln der KI-Verordnung (AI Act, Anhang III Nr. 4). Aus der früheren Vertriebs-Checkliste übernommen, als sie am 29.10.2026 entfiel.

5. Der Bewerbungs-Workflow

Eine Stelle wandert durch feste Status (Kanban auf der Pipeline-Seite):

Neu → Prüfen → Beworben → Interview → Angebot → (Zusage / Absage)
                                          ↘ Kein Match / Beirat abgelehnt / Nicht verfügbar / Geparkt

Der tägliche Ablauf (Tageslauf)

Der Tageslauf ist der Morgenlauf und orchestriert seriell:

  1. Jobsuche (WebSearch + Nejo + Arbeitsagentur, optional Apify) — drei Läufe nach Bucket (Remote · Deutschlandweit · Stadt +Umkreis), neue Treffer nach Vier-Augen als „Neu"
  2. Mail-Jobsuche — Job-Alert-Mails aus dem Postfach zu Stellen verarbeiten
  3. Zielfirmen-Sweep — rotierend 12 Karriereseiten prüfen
  4. Headhunter-Suche — rotierend 15 Headhunter-Seiten prüfen (eigener Agent)
  5. Beworben-Check (Phase 74) — wöchentliche Verfügbarkeitsprüfung aller laufenden Bewerbungen (Beworben/Interview): zuerst die Original-URL, bei geschlossenem Portal die Karriereseite (Phase-73-Mechanik); ein eigener 7-Tage-Vorab-Check spart den Lauf im Regelfall. Schreibt nur Verfügbarkeitsstatus + Prüfdatum — ändert nie den Bewerbungsstatus selbst
  6. Email-Check — Postfach der letzten 24–36 h, Antworten Bewerbungen zuordnen
  7. Ansichten-Refresh — Excel-Export, Tages-Digest, Volltext-Suchindex neu bauen
  8. Budget-Sync

Die headless/automatische Kette hinter dem Tageslauf (agent_runner.RECIPES["tageslauf"]) setzt nach dem Email-Check einmal je Kalenderwoche die Absagen-Analyse ein (P2-79; Vorprüfung ohne Modellstart, ein Fehlschlag hält die Kette nicht auf, s. docs/AUTOMATION.md) und hängt zusätzlich Coach-Site aktualisieren (Phase 81/82) als letztes, bewusst nicht-fatales Glied an — ohne vollständige Konfiguration oder bei abgeschaltetem Schalter endet der Schritt grün (Exit 0), ein echter Fehler danach markiert nur diesen einen Task, der Rest der Kette bleibt unberührt.

Ergebnis: eine kompakte Morgen-Zusammenfassung (Top-Treffer, Rotationsstände, Beworben-Check, Gmail, offene/überfällige Aktionen).

Pro Stelle: das Bewerbungspaket — Pflichtkern und optionale Bausteine

Pflichtkern (sequenziell, echte Datenabhängigkeit — Company-Fit als Kontext für den Match, der Entwurf aus cv-match als Grundlage für cv-erstellen):

Anzeigentext sichern (P2-75). Anlass: Eine Stelle aus einer Job-Mail bekam beim Erfassen von LinkedIn HTTP 429 („zu viele Anfragen"). Der Basis-Snapshot blieb ohne Anzeigentext (Befund QUELLE_VERTRAUT), Firma-Prüfung, CV-Match und CV erstellen liefen trotzdem durch und kannten die Anforderungen der Stelle nicht. Gemessen wurde eine Drosselung je Anfrage, keine Sperre (3 von 12, 3 von 11 und 9 von 18 LinkedIn-Abrufen in den letzten Mail-Jobsuchen, verstreut über den Lauf). Das Gegenmittel hat drei Teile; der Snapshot bleibt der eine Ort für den Anzeigentext, es entsteht kein zweiter Gliederungsweg. Spec: P2-75.

  • Wiederholen (pipeline/verify_jobs.py). check_url() wiederholt nur bei HTTP 429, mit den Pausen _PAUSEN_429 = (3, 8, 20) Sekunden; ein Retry-After als ganze Sekunden bis 30 ersetzt die jeweilige Pause. Bleibt es nach dem vierten Versuch bei 429, ist der Befund wie bisher NICHT_PRUEFBAR (Beleg „HTTP 429 nach 4 Versuchen (Rate-Limit)"). 403 (Bot-Block), Login-Wall, 404/410 und Abgelaufen-Marker werden nicht wiederholt, dort hilft Warten nicht. Das Ergebnis trägt versuche; wiederholen=False ergibt das frühere Verhalten mit genau einem Versuch. Die Pausen laufen über die Modulfunktion _schlafen, damit Tests sie ersetzen können. Die Stapel (check, bestand) holen erst alle Adressen und wiederholen nur die geblockten in bis zu drei weiteren Runden nach den Pausen _RUNDEN_PAUSEN = (5, 10, 20); die Pausen je Lauf bleiben so bei höchstens 35 s (Messung am 14.10.2026 mit 24 Adressen: 9 → 2 → 0 geblockt in 58 s). Die Zusammenfassung nennt wiederholt und rate_limit_offen. Die vier Such-Skills rufen verify_jobs check deshalb mit einem Zeitlimit von 300000 ms auf.
  • Nachholen (pipeline/posting_snapshot.py). hat_anzeigentext(job) ist eine reine Lesefunktion: wahr, wenn der Snapshot Text trägt (Basis-Karte, Block „Volltext (unbereinigt)", Volltext-Kandidaten älterer Snapshots oder eine grün gegliederte Fassung). anzeigentext_sichern(job_id) liefert vorhanden (kein Netzabruf), nachgeholt oder fehlt mit einem Grund in Klartext. Ersetzt wird der Snapshot nur bei Befund OK mit Text (render_basis(job, text, hinweis=…), an Ort und Stelle, dazu ein JobLog der Art auto); jeder andere Befund lässt die Datei bytegleich. Eine Stelle ohne Snapshot bekommt auf demselben Weg ihren ersten. Gegliedert wird der Text erst bei der nächsten Firma-Prüfung. Für den Bestand gibt es python -m pipeline.posting_snapshot nachholen [--job-id N | --status CSV] [--dry-run] neben backfill (der nur Stellen ganz ohne Snapshot anlegt); mit --job-id ist der Exit-Code 3, wenn der Text fehlt.
  • Halt beim Start (app/main.py). Die Konstante ANZEIGE_KINDS (firma-pruefen, cv-match, cv-erstellen, anschreiben-erstellen) ist bewusst dieselbe Menge wie LOW_MATCH_KINDS, aber eine eigene Konstante. _guard_anzeigentext() läuft in create_task() direkt nach _guard_low_match() mit derselben aufgelösten Schrittmenge, gilt also für Einzel-Tasks, Ketten und „Erneut". Er ruft anzeigentext_sichern über run_in_threadpool auf, weil der Abruf mit Pausen gut 30 s dauern kann und sonst den ganzen Server anhielte. Bei fehlt antwortet er mit 409 und dem Marker ANZEIGE_FEHLT; die Bestätigung ist params.ohne_anzeigentext_ok=true (Muster LOW_MATCH, kein Claude-Lauf und keine Kosten vor der Entscheidung). AgentTaskButton zeigt die Rückfrage inline mit „Trotzdem starten" und „Abbrechen"; bestätigte Overrides sammeln sich, wer LOW_MATCH und ANZEIGE_FEHLT nacheinander bestätigt, startet mit beiden. Dass Firma-Prüfung ebenfalls anhält, ist eine Entscheidung vom 14.10.2026: Ohne Anzeige bewertete sie die Rolle blind.
  • Skills lesen den Snapshot zuerst. firma-pruefen (Schritt 3b), cv-match (Schritt 1), cv-erstellen und anschreiben-erstellen nehmen den Anzeigentext aus job.posting_snapshot_path. Fehlt er trotz Server-Nachholen, rufen sie einmal nachholen --job-id auf. WebFetch auf job.url ist nur noch Teilquelle (Badge amber).   • Ausnahme-Regel. httpx.ReadTimeout und httpx.RemoteProtocolError (das Portal nimmt die Verbindung an, antwortet aber nicht oder schließt sie ohne Antwort) ergeben NICHT_PRUEFBAR mit einem Beleg, der den Bot-Schutz benennt, nicht mehr TOT. 8. Betrieb, Automatik & Sicherheit

Betrieb im Alltag

Starten und Beenden (kein Auto-Reload — nach jeder Backend-Änderung ist ein Neustart nötig):

macOS Windows
Starten start.command · start_lan.command (WLAN) start_windows.bat
Beenden Ctrl+C im Server-Fenster, sonst stop.command Strg+C, sonst stop_windows.bat

Die Stop-Skripte sind für den Fall gedacht, dass das Server-Fenster nicht mehr erreichbar ist (geschlossen, im Hintergrund gestartet, hängend). Sie beenden den Prozess auf dem Server-Port (Standard 8000) erst freundlich und nach 10 s hart — vorher prüfen sie aber, ob gerade Agent-Läufe aktiv oder eingereiht sind, und fragen nach. Grund: Skill-Läufe hängen als Kindprozesse am Server, und eine Beirats-Debatte läuft sogar in ihm selbst; ein Neustart bricht sie ab. Mit --force überspringt man die Rückfrage; ein anderer Port geht über PORT=8010 ./stop.command.

Für Skript-/Terminal-Nutzung ohne Doppelklick:

lsof -ti :8000 -sTCP:LISTEN | xargs -r kill; sleep 1
cd backend && nohup ~/.bewerbung_mgmt_venv/bin/python run_server.py > /tmp/bms_server.log 2>&1 & disown

Umgebungsvariablen. .env.example listet die Einstellungen, die vom Standard abweichen dürfen (Server-Port und -Adresse, BMS_DATA_DIR, BMS_SECRETS_DIR, Grenzen für Agent-Läufe). Das Programm liest sie ausschließlich aus der Umgebung (os.environ); eine Datei .env lädt es nicht selbst. Die Werte müssen deshalb in jeder Shell gesetzt sein, die den Server startet.

Backup & Restore, manuell über scripts/backup_db.sh (Kopie über SQLites Online-Backup-API, konsistent auch bei parallelen Schreibzugriffen). Die automatische Sicherung steht unten im Abschnitt „Backups“.

scripts/backup_db.sh                    # Backup anlegen: data/backups/bewerbung_backup_<JJJJMMTT_HHMMSS>.sqlite
scripts/backup_db.sh --label vor_x       # mit Suffix, z. B. vor einer riskanten Operation
scripts/backup_db.sh --rotate            # + Rotations-Kandidaten auflisten (Dry-Run, löscht nichts)
scripts/backup_db.sh --rotate --apply    # + Kandidaten wirklich löschen (behält die neuesten 15)
scripts/backup_db.sh --rotate --apply --keep 20   # andere Aufbewahrungsmenge

Für das Zurückspielen gibt es wiederherstellen.command bzw. wiederherstellen_windows.bat (Abschnitt „Backups“); von Hand geht es so: Server stoppen, gewünschtes Backup zurückkopieren (cp data/backups/<datei>.sqlite data/bewerbung.sqlite), Integrität prüfen (sqlite3 data/bewerbung.sqlite "PRAGMA integrity_check;" → ok), Server neu starten. Manuelle Backups werden nie automatisch gelöscht — Rotation löscht ausschließlich mit explizitem --apply.

sqlite3-CLI gegen die LAUFENDE App (Phase 67F): Die App setzt einen expliziten busy_timeout (15 s, backend/app/db.py), die sqlite3-CLI kennt diesen Wert nicht (eigener Prozess, eigene Verbindung) und hat von Haus aus 0 — eine Ad-hoc-Abfrage gegen data/bewerbung.sqlite, während der Server läuft und gerade schreibt, kann sofort mit „database is locked“ abbrechen. Bei einer Abfrage gegen die laufende App deshalb voranstellen:

sqlite3 data/bewerbung.sqlite "PRAGMA busy_timeout=5000; SELECT ...;"

Beim Restore ist das nicht nötig (der Server ist dann bewusst gestoppt).

Outbound-Check (scripts/outbound_check.py, Phase 66B) liest die Agent-Task-Logs unter ~/.bewerbung_mgmt_logs/ (nur lesend) und listet, wohin headless laufende Skills tatsächlich ausgehende Verbindungen (curl/WebFetch) aufgebaut haben, gegen eine gepflegte Liste erwarteter Ziele:

python3 scripts/outbound_check.py            # Kurzübersicht + auffällige Treffer
python3 scripts/outbound_check.py --all       # vollständige Host-Liste statt Top-20
python3 scripts/outbound_check.py --days 7    # nur die letzten 7 Tage

Kein Automatismus, kein Cron, keine Alarmierung — ein Werkzeug, das bei Bedarf manuell läuft. Es ist Erkennung, keine Vorbeugung (ehrliche Einordnung: „Was die Skill-Freigabeliste leistet — und was nicht“ unten).

Beim Kunden spielt scripts/bms_update.py (nur Standardbibliothek, kein Import aus app/ pipeline — das Skript läuft neben einer halb ersetzten Installation) ein neues Paket ein: Installation prüfen (kein Git-Checkout, läuft in der venv) → Paket finden (P2-82: ein Pfad-Argument gilt ohne jeden Netzkontakt; sonst gewinnt die höchste Version aus dem neuesten GitHub-Release und aus ~/Downloads/BMS_*.zip, ein geladenes Paket liegt unter data/updates/pakete/ und gilt danach wie ein übergebenes, Einzelheiten im Abschnitt „Update-Auskunft über GitHub-Releases“ unten) → Selbstaktualisierung (weicht das Skript im Paket vom laufenden ab, wird mit --delegiert an die neue Fassung übergeben, damit immer die Update-LOGIK der neuen Version gilt; den Pfad des Pakets bekommt sie ausdrücklich als Argument, sonst suchte und lüde sie ein zweites Mal) → Paket prüfen (Manifest, SHA-256, keine unsicheren/ geschützten Pfade, Version/Vorschau) → Server-aus-Check (GET /api/health) → Plan erstellen und zeigen (--pruefen endet hier) → Rückfrage (übersprungen mit --ja) → Sperre → Sicherung (Datenbank-Kopie über die sqlite3-Backup-API, jede ersetzte/entfernte Datei, altes Manifest, ggf. alter frontend/dist) → Dateien atomar schreiben → Abhängigkeiten (pip install, npm ci, Oberfläche neu bauen, je nach dem, was sich geändert hat) → Selbsttest → Abschluss (neues Manifest, bericht.json, Sperre lösen). Jeder Fehler ab „Dateien schreiben" rollt vollständig zurück (Exit 2) statt eine Kundeninstallation halb fertig zu lassen. Der Selbsttest (backend/app/selbsttest.py, python -m app.selbsttest) läuft in einem EIGENEN Subprozess gegen eine Kopie der gesicherten Datenbank (BMS_DATA_DIR/BMS_LOG_DIR/BMS_SECRETS_DIR auf Temp-Verzeichnisse) — er importiert app.main (fängt fehlende Pakete/Syntaxfehler) und prüft init_db() gegen SQLModel.metadata (fängt eine vergessene _ADD_COLUMNS-Migration). Gestartet wird über update.command (zsh) bzw. update_windows.bat (CRLF, s. u.) — beide reichen nur den Programmordner durch und laufen komplett in einer Funktion bzw. einem geklammerten Block, weil das Update die aufrufende Datei selbst ersetzen kann, während sie noch läuft. --zurueck nimmt das letzte erfolgreiche Update zurück; die Rückfrage, ob dabei auch die Datenbank auf den Stand davor zurückgesetzt wird, beantwortet ausschließlich der eigene Schalter --mit-datenbank — --ja gilt nur für die Einspiel-Rückfrage, nie für die Datenbank-Rückfrage (zwei getrennte Risikostufen).

GET /api/version (app/version.py + dünner Router app/routes_version.py) beantwortet, welche Fassung gerade läuft: „paket" (liegt bms_manifest.json im Programmordner, Werte von dort, commit auf 7 Zeichen gekürzt), „git" (liegt .git, version aus VERSION, commit/datum über git rev-parse/git show, entwicklungsstand aus git describe --tags --long --dirty) oder „unbekannt". Jeder Git-Aufruf läuft mit 5-s-Timeout und fängt jeden Fehler ab — die Einstellungen-Seite darf an dieser Auskunft nie mit einem 500 scheitern.

Die Freigabe selbst ist das Werkzeug des Herausgebers (pipeline/release.py über scripts/release.sh: freigeben/notizen/abholen) und der Workflow .github/workflows/release.yml (Tag-Push v*.*.* oder workflow_dispatch für einen Probebau). Zum Anwender gelangt das Paket seit P2-82 über das GitHub-Release selbst: Die Freigabe endet mit dem Release, ein Ablegen auf einem Server gibt es nicht mehr (der Paketdienst von P2-71 ist ausgebaut). Das Update-Werkzeug und die Installationsanleitungen laden das Paket dort, der Knopf in den Einstellungen zeigt die neueste Version an (Abschnitt „Update-Auskunft über GitHub-Releases“). Ausführlich in docs/RELEASE.md.

Was die Skill-Freigabeliste leistet — und was nicht (Phase 66)

automation/agent_settings.json schaltet für headless laufende Skills (claude -p) eine Berechtigungsliste scharf: nur explizit erlaubte Werkzeuge/Kommandos dürfen laufen, alles andere ist automatisch verboten. Wichtig ist hier eine ehrliche Grenze (s. Bau-Spec Phase 66, „Die ehrliche Ausgangslage"):

  • Was sie leistet: Schutz gegen Unfälle. Ein Skill, der versehentlich rm, git push oder chmod auslösen würde, wird gestoppt, bevor etwas passiert — belegt im echten Lauf vom 10.07.2026, als Artifact (Veröffentlichung nach außen) korrekt geblockt wurde.
  • Was sie NICHT leistet: keine Grenze gegen eine gezielte Prompt-Injection. Die Skills verarbeiten unbeaufsichtigt fremden Text (Stellenanzeigen, eingehende Mails, Firmenwebsites); Bash(python:*) bleibt bewusst uneingeschränkt erlaubt, weil das dokumentierte Muster für DB-Schreibzugriffe ein Python-Heredoc ist. Ein Python-Einzeiler kann alles, was curl kann, und mehr — nur curl zu sperren wäre Theater, dieselbe Exfiltration ginge zwei Zeilen später über Python. Diese Liste verkleinert also ausschließlich den Schaden bei einem Fehler, nicht das Risiko einer absichtlichen Umgehung.

Was Phase 66 stattdessen liefert (Schadensbegrenzung, Kennzeichnung, Erkennung statt einer vorgetäuschten Sicherheitsgrenze):

  • 66A — Schadensradius: agent_runner._child_env(kind) reicht pro Skill-Subprozess nur noch die für DIESE Art freigegebenen Secrets aus agent.env weiter (Tabelle SECRET_KEYS_BY_KIND, einzige Zuordnung aktuell: jobsuche-apify → APIFY_TOKEN), statt wie bisher jeden Schlüssel an jeden Subprozess zu geben — mit lauter Meldung im Task-Log, falls ein Skill doch mehr braucht. 9 von 22 headless-Arten bekommen zusätzlich disallowed_tools (WebSearch/WebFetch gesperrt, wo der Skill sie nachweislich nicht nutzt).
  • 66B — Kennzeichnung: agent_runner.HEADLESS_SUFFIX (hängt an JEDEM headless-Prompt) markiert jeden per WebFetch/WebSearch/curl/gmail_client geladenen Fremdtext ausdrücklich als Datenmaterial, nicht als Anweisung, mit der Aufforderung, eingebettete Anweisungen zu ignorieren und im Bericht zu melden — ergänzt an den zwei konkretesten Einbettungsstellen (firma-pruefen/ SKILL.md Anzeigen-Snapshot, email-check/SKILL.md Mail-Klassifikation). Das ist Hygiene, keine Garantie — eine Verhaltensregel für das Modell, keine technische Schranke.
  • 66B — Erkennung: scripts/outbound_check.py liest die Agent-Logs (nur lesend) und listet ausgehende Ziele (curl/WebFetch) gegen eine gepflegte Liste erwarteter Hosts — kein Automatismus, kein Cron, keine Alarmierung, ein Werkzeug für den manuellen Blick bei Bedarf.

Ausdrücklich offen (nicht Teil von Phase 66, hier nur benannt statt wegdefiniert):

  • gmail.compose-Scope: erlaubt der Google-API technisch mehr als Entwürfe (auch Senden) — die einzige Grenze ist der fehlende Codepfad in pipeline/gmail_client.py (keine send-Funktion, kein /send-Endpunkt), nicht die Technik. Seit Phase 71F gilt dieselbe Garantie für den IMAP-Provider pipeline/imap_mail.py (Entwürfe nur per APPEND, kein smtplib-Import in backend/pipeline/ — als Negativ-Wächter in tests/test_kein_sendcodepfad.py verankert). Solange ein Skill-Subprozess mit freiem python/curl läuft, ist dieser Codepfad grundsätzlich umgehbar.
  • Gmail-Zugriff ist datei-, nicht env-basiert: gmail_client.py liest gmail_credentials.json/ gmail_token.json direkt aus dem Secrets-Verzeichnis. _child_env(kind) (66A) kann diesen Zugriff deshalb strukturell NICHT einschränken — jeder Skill-Subprozess läuft als der angemeldete Benutzer und kann die Dateien lesen wie jedes andere lokale Programm auch.
  • Optionen dafür, ohne dass Phase 66 sie umsetzt: Skills schrittweise von freien Python- Heredocs auf eine schmale, geprüfte Schnittstelle umstellen (z. B. ein CLI mit fester, auditierbarer Befehlsmenge statt beliebigem Code) — das würde Bash(python:*) überhaupt erst einschränkbar machen, ist aber eine eigene, große Phase, keine Erweiterung dieser Liste.

Aufbewahrung (reine, ohne Dateizugriff testbare Funktion zu_entfernen()): immer die neueste, alle der letzten 24 h, je Kalendertag die neueste für 7 Tage, je ISO-Woche für 4 Wochen, monatlich einstellbar (Standard

0) — ausgedünnt wird nur NACH einer erfolgreichen neuen Sicherung. Gelöschte Netzwerk-Einträge (Zielfirmen, Headhunter, Kontakte) sind seit 18.07. je Tab in einem aufklappbaren Papierkorb-Panel sichtbar und per Klick wiederherstellbar — bewusst ohne Endgültig-Löschen in der UI, denn die Tombstones verhindern, dass ein früherer Drive-Import oder der Datei-Import (P2-62) Gelöschtes wiederbelebt. Sicherung zurückspielen (P2-66, scripts/bms_wiederherstellen.py): Standardbibliothek-Werkzeug wie bms_update.py, gestartet über wiederherstellen.command (zsh) bzw. wiederherstellen_windows.bat (CRLF, Block in runden Klammern) mit --installation <ordner> [--liste] [--datei <name>] [--ja]. Es nutzt Helfer aus bms_update (_server_laeuft, _data_dir, _sperren/_entsperren, _rueckfrage, _pfad_unsicher, _selbsttest_ausfuehren) und läuft bewusst auch in einer Git-Installation, weil es nur Daten betrifft. Ablauf: Server-Check (GET /api/health, läuft er, Abbruch) → Sperre data/updates/.update.lock, geteilt mit dem Update, sodass sich beide ausschließen → Kandidaten sammeln (automatische Sicherungen data/backups/auto/*.zip, manuelle *.sqlite/*.zip direkt in data/backups, ZIPs dort nur mit genau bewerbung.sqlite als Inhalt, damit Ordner-Sicherungen anderer Werkzeuge nicht erscheinen; nicht die Update-Sicherungen in data/updates, dafür gibt es update --zurueck) → nummerierte Liste, neueste zuerst (--liste endet hier) → Auswahl → Prüfung in einem Temp-Verzeichnis (genau ein Eintrag bewerbung.sqlite, SQLite-Header, PRAGMA integrity_check, Tabelle job, Selbsttest auf einer Kopie, der eine ältere DB additiv migriert) → Rückfrage (übersprungen mit --ja) → aktuellen Stand sichern als data/backups/bewerbung_backup_<JJJJMMTT_HHMMSS>_vor_wiederherstellung.sqlite (Namensmuster passt zu cleanup._backup_dateien) → Einsetzen über Temp-Datei und os.replace, vorhandene -wal/-shm werden mit Zeitstempel umbenannt, nicht gelöscht → Protokoll data/backups/wiederherstellung_<stempel>.json (zeitpunkt, quelle, quelle_zeitpunkt, sicherung_vorher, ergebnis; in derselben Sekunde mit _2, _3). Bei einem Fehler nach dem Ersetzen wird die Sicherung vom Beginn zurückkopiert. Rücknahme ohne eigenen Schalter: Die Sicherung „vor Wiederherstellung“ erscheint beim nächsten Aufruf in der Liste. Exit-Codes: 0 = OK oder nur Liste, 1 = abgebrochen (Nein, Server läuft, Sperre belegt, keine Sicherung, Prüfung fehlgeschlagen, data/ unverändert), 2 = Fehler beim Einsetzen (Ausgangszustand wiederhergestellt), 3 = falscher Aufruf. Nur die Datenbank wird ersetzt, outputs/ und Uploads bleiben. Warum kein Knopf in der App: app/db.py bindet die Datenbank beim Import in einer einzigen Engine ohne dispose/Reinit, ein Tausch im laufenden Betrieb wäre riskant. Beide Starter und das Skript stehen in PFLICHTDATEIEN, die .command in _STARTDATEIEN_AUSFUEHRBAR (pipeline/kundenpaket.py).

Entfernen (POST /api/beispieldaten/entfernen, beispieldaten.entfernen(), ein Lock gegen doppelten Aufruf):

  1. Nur bei vorhanden, sonst ValueError → 409. Läuft an einer Beispielstelle eine Aufgabe (queued/running), ebenfalls 409: Sie schriebe nach dem Löschen an eine Stelle, die es nicht mehr gibt.
  2. Sicherung über app.sicherung.anlegen(), also in der Reihe der automatischen Sicherungen unter data/backups/auto, wie „Jetzt sichern“. SicherungLaeuft → 409, jeder andere Fehler → 500. In beiden Fällen bleibt alles unverändert.
  3. Eine Transaktion. Gelöscht wird nur, was Id UND Zweitmerkmal trägt (_beispiel_bedingungen: job.dedup_key LIKE 'beispiel|%', Firmenname aus der Liste, email.from_addr LIKE '%beispiel.de%', contact.email LIKE '%beispiel.de', Netzwerk-Kontakt nach Name, bei Skills und Werdegang quelle = 'beispiel'). Grund: SQLite vergibt die Id der zuletzt gelöschten Zeile erneut. Löschte ein Kunde den letzten Beispiel-Skill von Hand und trüge danach einen eigenen ein, bekäme er dieselbe Id. Dazu kommt alles, was an einer Beispielstelle hängt: jede Tabelle mit job_id außer email und agenttask, aus models.py ermittelt und Kinder zuerst. Mails ohne Beispielmerkmal an einer Beispielstelle und Aufgaben (Kosten-Historie im Task-Center) werden gelöst (job_id und application_id leer), nicht gelöscht. Eigene Zeilen mit company_id auf eine Beispielfirma verlieren nur den Verweis. Die Profilfelder werden nur geleert, solange sie noch den Beispielwerten entsprechen. Das ist hartes Löschen ohne Tombstone, anders als „Stelle löschen“ (Phase 32): Die Sicherung ist der Rückweg.

Dateien erst NACH dem Commit: Scheitert ein Verschieben, bleibt eine Datei liegen statt einer Datenbank, die auf Gelöschtes zeigt. config/profil.md und der Basis-CV wandern nur in den Papierkorb, wenn ihr SHA-256 noch dem angelegten entspricht, sonst bleiben sie und stehen in behalten. Die Verschiebung ist eine eigene (data/papierkorb/<JJJJMMTT>_<Name> (ältere Einträge tragen noch JJJJ_MM_TT_)), nicht der Helfer der Lösch-Endpunkte: Der lässt nur die Ordner der Positivliste zu, die Profil-Datei liegt in config/. Auch die Artefakte, die ein Kunde an einer Beispielstelle erzeugt hat (Pfadspalten *_path der gelöschten Zeilen), wandern in den Papierkorb, geprüft von _artefaktpfad_pruefen: nur Dateien unter data/ und outputs/ (der aufgelöste Pfad zählt), nie data/papierkorb/, data/backups/, die Datenbank oder die Basis-CVs.

Tests: tests/test_beispieldaten.py (Bedingungen, Inhalt, Basis-CV, Entfernen, Router und der Erst-Start im Subprozess nach dem Muster von tests/test_neuinstallation.py).

Bis P2-68 legte der Kunde config/profil.md von Hand im Texteditor an, und es kam auf die Schreibweise **Name:** an. Kein Endpunkt schrieb die Datei. Module. pipeline/profil_datei.py (Vertrag F: reine Funktionen für Zerlegen und Zusammensetzen plus lesen() und schreiben(), kein Import aus app) und app/routes_profil_identitaet.py (Vertrag A, Router wie routes_sicherung.py, in main.py nur Import und include_router). Den Pfad liest profil_datei zur Laufzeit aus user_profile._PROFIL_MD, damit Tests ihn mit demselben Patch umlenken wie bisher.

Verlustfreie Zerlegung. Die Maske ändert nur, was sie anzeigt. Alles andere bleibt Byte für Byte gleich: unbekannte Abschnitte, unbekannte Zeilen in bekannten Abschnitten, Sprachen / CV-Fassungen, die Empirie, Leerzeilen, Zeilenenden (LF oder CRLF) und der Dateikopf. Einzige Ausnahme im Kopf: Die Titelzeile # Kandidatenprofil: <Name> zieht mit, wenn der Name in der Maske geändert wird und die Zeile genau den bisherigen Namen trägt. Speichern ohne Änderung in der Maske ergibt exakt dieselbe Datei.

  • Zerlegt wird in den Kopf (alles vor der ersten Zeile ##) und die Abschnitte. Erkannt werden sie am Überschriftentext (getrimmt, ohne Rücksicht auf Groß-/Kleinschreibung, „beginnt mit“): Identität (Feldzeilen: Name, Positionierung, Standort als „Anschrift“, Kontakt als E-Mail und Telefon, LinkedIn, Aktuell; weitere Feldzeilen als weitere mit editierbarem Wert), Kurzprofil, Harte Rahmenbedingungen und Bekannte Skill-Gaps (jeweils Freitext) sowie aus Zielrolle nur die Zeile Zieltermin. Ältere Zeilen wie Ebene oder Branche bleiben unberührt in der Datei, Titel, Ebene und Branche kommen aus den Suchplänen. Alle anderen Abschnitte bleiben unverändert, die API meldet nur ihre Überschrift (unveraendert).
  • Eine Feldzeile ist ^(\s*[-*]\s*)\*\*(.+?):\*\*[ \t]*(.*)$. Beim Ändern wird nur der Wert ersetzt, Einrückung, Aufzählungszeichen und Schlüssel bleiben. Ein neues Feld kommt hinter die letzte Feldzeile des Abschnitts. Ein vorhandenes Feld mit leerem Wert behält seine Zeile, nur bei den optionalen Feldern Positionierung, LinkedIn und Aktuell entfällt sie. Ein neues Feld mit leerem Wert wird nicht angelegt.
  • Kontakt: Beim Lesen wird an · oder | geteilt, der erste Teil mit @ ist die E-Mail, der Rest (mit · verbunden) das Telefon. Geschrieben wird E-Mail · Telefon, bei nur einem Wert ohne Trenner.
  • Freitext-Abschnitte gehen ohne die Leerzeilen an Anfang und Ende an die Maske. Beim Schreiben bleibt die bisherige Zahl der Leerzeilen vor und nach dem Rumpf erhalten, ein unveränderter Text lässt den Abschnitt bytegleich. Neue Zeilen erhalten das in der Datei vorherrschende Zeilenende.
  • Fehlt die Datei, liefert lesen() vorhanden=False, leere Werte und den Zieltermin, und schreiben() erzeugt die Vorlage (Aufbau wie in beispieldaten._profil_md_text(), mit den Abschnitten Identität, Kurzprofil, Zielrolle, Harte Rahmenbedingungen, Sprachen / CV-Fassungen, Bekannte Skill-Gaps / Red Flags und Empirie). Fehlt in einer vorhandenen Datei ein bekannter Abschnitt, legt schreiben() ihn nur an, wenn die Maske Inhalt liefert, vor der Empirie oder sonst am Dateiende.

Schreiben und Prüfungen. schreiben() ersetzt atomar (Temp-Datei im selben Ordner, os.replace, UTF-8). Vorher geht eine Kopie der alten Datei in den Papierkorb data/papierkorb/ (Datumspräfix JJJJMMTT_ wie bei _freier_name); nichts wird hart gelöscht. Ein ValueError mit Kundentext (Sie-Form) meldet: Name fehlt (Pflicht), Zeilenumbruch in einem einzeiligen Feld, Länge über 300 Zeichen (einzeilig) bzw. 5000 (Freitext), ein Schlüssel in weitere oder zielrolle, den es weder in der Datei noch unter den Standard-Schlüsseln gibt, und eine Freitext-Zeile, die mit ## beginnt (sie würde einen neuen Abschnitt anlegen). Nicht blockierende hinweise: Die Anschrift hat kein Komma oder keine Postleitzahl (die Ortszeile der Anschreiben entsteht aus Straße Nr, PLZ Ort), oder die E-Mail hat kein @.

API (GET/PUT /api/profil/identitaet). Die Antwort trägt vorhanden, stand, identitaet (name, positionierung, anschrift, email, telefon, linkedin, aktuell, weitere), kurzprofil, zielrolle (Liste aus schluessel und wert), rahmenbedingungen, skill_gaps, unveraendert und hinweise. stand ist der SHA-256 des Dateiinhalts, leer bei fehlender Datei. Das PUT nimmt denselben Aufbau mit stand entgegen. Ein veralteter stand ergibt 409 („Die Profil-Datei wurde inzwischen geändert. …“) und lässt die Datei unverändert: Zwischen Laden und Speichern kann ein Skill die Empirie ersetzt haben, und das darf die Karte nicht stillschweigend überschreiben. Dateiauslieferung: nur Dokumente, nur aus frontend/dist (P2-54)

Der Server liefert Dateien an genau zwei Stellen aus. GET /api/artifact gibt nur Dateien aus den Ordnern der Positivliste _ARTEFAKT_ORDNER in main.py heraus, und dort nur die Dateitypen, die die Oberfläche öffnet: Berichte (.html) aus company_fit, job_postings, interview_prep, beirat, analysen und transcripts (dort auch .md), Upload-Typen aus job_files und profil/dateien, Word/PDF aus cv_basis, tmp (registrierte CV-Entwürfe), outputs/cv, outputs/cv_entwuerfe und outputs/anschreiben. Alles andere liefert 403, auch wenn die Datei existiert: Datenbank, Sicherungen, Updates, sicherung.json, Rohdaten, Papierkorb. Geprüft wird der aufgelöste Pfad (.., Symlinks, Backslashes), und zwar vor der Existenz. Wer einen neuen Ordner für Artefakte einführt, muss ihn dort eintragen, sonst bleibt er unerreichbar. Der SPA-Fallback (main.spa) liefert nur Dateien innerhalb von frontend/dist, alles andere bekommt index.html. Bis P2-54 gingen dort %2e%2e- und %2F-Pfade durch, also jede lesbare Datei des Rechners. Der LAN-Modus bleibt trotzdem ohne Anmeldung: Oberfläche und API sind im Netz offen, nur ganze Datenbanken, Sicherungen und fremde Dateien lassen sich nicht mehr abrufen. GET /api/doku/{name} (P2-59) gehört nicht dazu: Es liefert keine Datei, sondern die Seite zu einem Eintrag aus einem festen Katalog, der Name aus der Adresse wird nie als Pfad benutzt (s. „Dokumentationsseite“ unten).

Keine Freigabe für fremde Webseiten (CORS, P2-55)

Das Backend sendet keinen Access-Control-Allow-Origin-Header. Eine fremde Webseite im selben Browser bekommt die Antworten der API deshalb nicht zu sehen, und Anfragen, die einen Preflight brauchen (JSON-Inhalt, PATCH, DELETE), schickt der Browser gar nicht erst ab. Die eigenen Aufrufer brauchen keine Freigabe: Die Oberfläche kommt vom selben Server, auch im LAN-Modus unter http://<name>.local:8000; der Vite-Dev-Server leitet /api per Proxy weiter; Skills und Skripte nutzen curl oder Python, für die CORS nicht gilt. Bis P2-55 stand in main.py eine CORSMiddleware mit allow_origins=["*"] und allen Methoden: Jede Webseite konnte Stellen, Mails und Profil lesen, KI-Läufe starten und Stellen löschen, sogar eine lokal geöffnete HTML-Datei (Origin: null). Wer eine Herkunft freigeben muss, trägt sie einzeln ein, nie *, und passt tests/test_keine_cors_freigabe.py an. Was CORS nie geschützt hat, fängt seit P2-57 die Herkunftsprüfung ab (nächster Abschnitt): Einfache Anfragen ohne Preflight (POST ohne Inhalt, als Formular oder Upload) schickt der Browser trotzdem ab, nur die Antwort bleibt der fremden Seite verborgen.

Herkunfts- und Host-Prüfung (P2-57)

Vor jeder Route prüft die Middleware _Herkunftspruefung in main.py zwei Dinge, bei einem Verstoß antwortet sie mit 403 und einer Meldung in detail.

Host (jede Anfrage, auch Oberfläche und Assets): Der Server antwortet nur unter einer IP-Adresse, localhost, einem Namen auf .local oder einem Rechnernamen ohne Punkt. Diese Namen kann eine fremde Domain nicht per DNS-Rebinding vortäuschen: Stellt sie ihren DNS-Eintrag nach dem Laden auf 127.0.0.1 um, ist ihre Seite für den Browser derselbe Ursprung und läse die API ohne jede CORS-Freigabe, im lokalen wie im LAN-Modus. Die Adressen, die start_lan.command anzeigt, gehen immer. Weitere Namen (Router-Name wie mac.fritz.box, Tailscale, Reverse-Proxy) gibt die Umgebungsvariable BMS_HOSTS frei, getrennt durch Komma oder Leerzeichen: am Mac im Terminal BMS_HOSTS=mac.fritz.box ./start_lan.command (per Doppelklick im Finder kommt keine Umgebungsvariable an), unter Windows set BMS_HOSTS=mac.fritz.box in derselben Eingabeaufforderung vor dem Start.

Origin (alles außer GET, HEAD, OPTIONS): Schickt der Browser einen Origin, müssen Host und Port zum Host-Header passen. Das Schema zählt nicht, und ein fehlender Port gilt als Standardport des Origin-Schemas, damit ein Proxy mit TLS davor funktioniert. Origin: null (lokal geöffnete HTML-Datei, Sandbox-iframe, seit P2-58 jeder Bericht) ist gesperrt. Ohne Origin (curl, Skills, Skripte, Python) geht die Anfrage durch. Einzige Ausnahme ist http://localhost:5173, der Vite-Dev-Server über seinen Proxy: nur an Host localhost (darauf schreibt der Proxy den Host um) und nur mit Sec-Fetch-Site: same-origin oder ohne diesen Header. Ein anderes Projekt auf Port 5173, das den Server direkt anspricht, meldet same-site; an einen .local-Namen oder eine LAN-IP schicken Browser gar kein Sec-Fetch-Site, deshalb die Bindung an localhost. Der Port 5173 gehört zur Ausnahme: vite.config.ts setzt strictPort, damit Vite bei belegtem Port abbricht, statt still auf 5174 auszuweichen (dann bekäme jeder Schreibzugriff 403).

Bis P2-57 konnte jede Webseite 21 Routen blind auslösen, darunter discard (jede Stelle auf „Kein Match"), den Basis-CV mit overwrite ersetzen, den ZIP-Import (Lauf skills-sortieren), POST /api/sicherung und die Verbindungstests für Coach-Site und Mail. Hinter einem Reverse-Proxy muss dieser den Host-Header samt Port durchreichen (Caddy tut das von sich aus, nginx braucht proxy_set_header Host $http_host;), und sein Name gehört in BMS_HOSTS. Restrisiko: Wer im selben Netz mDNS- oder LLMNR-Antworten fälscht, kann über einen .local- oder punktlosen Namen weiter umbiegen; im LAN-Modus hat so jemand ohnehin direkten Zugriff. Vertrag: tests/test_herkunftspruefung.py, mit einem Wächter über alle Operationen aus dem OpenAPI-Schema. Die Lizenzprüfung, die von P2-67 bis 1.7.0 innerhalb dieser Prüfung saß (402), ist seit P2-82 ausgebaut (Abschnitt „Lizenz — ausgebaut“).

Berichte in der Sandbox (P2-58)

HTML-Berichte aus /api/artifact und der Tages-Digest (/api/digest) tragen den Header Content-Security-Policy: sandbox allow-scripts allow-popups allow-popups-to-escape-sandbox (_BERICHT_SANDBOX in main.py). Der Browser gibt ihnen damit einen eigenen, undurchsichtigen Ursprung (null) statt dem der API. Ein Skript in einem Bericht, etwa über eine Prompt-Injection aus Webinhalten, die ein KI-Lauf übernommen hat, erreicht die API dann nicht mehr: Lesen scheitert an der fehlenden CORS-Freigabe (P2-55), Schreiben an der Herkunftsprüfung (Origin: null → 403, P2-57). Bis P2-58 lief so ein Skript im Ursprung der API, las Stellen, Mails und Profil und schrieb mit passendem Origin an der Prüfung vorbei; im Browser nachgestellt verwarf ein Probebericht eine Stelle. Dazu kommt Cache-Control: no-cache (beides in _BERICHT_KOPF): Ohne ihn zeigte Chrome einen früher geöffneten Bericht mit den alten Headern aus dem Cache, also ohne Sandbox.

Weiter gehen (in Chrome 154 gemessen): Skripte (71 ältere Berichte bis 08.08.2026 bauen ihren Inhalt per Skript auf), Links in neuen Tabs (diese Tabs sind normale Seiten, dafür allow-popups-to-escape-sandbox), Links im selben Tab, Drucken über das Browsermenü und das eingebettete Favicon. Nicht mehr gehen, von keinem Bericht genutzt: Formulare, alert und confirm, window.print() aus einem Skript (bräuchte allow-modals), localStorage, Cookies, Schriften oder Daten per fetch vom BMS-Server (beides braucht CORS). Wer so etwas in einen Bericht einbaut, braucht eine eigene Freigabe; allow-same-origin nie, es höbe den Schutz auf. PDF, Bilder, Word und Downloads (download=true) bleiben ohne Header, ebenso die Oberfläche selbst (index.html, /assets). Eine neue HTML-Route setzt _BERICHT_KOPF; ein Wächter in tests/test_bericht_sandbox.py meldet jede HTMLResponse außerhalb von artifact, digest und (seit P2-59) routes_doku.dokument, der Dokumentationsseite (nächster Abschnitt). Restrisiken: Ein eingeschleustes Skript kann den Inhalt seines eigenen Berichts weiter nach außen schicken oder die Seite umleiten. Berichte, die der Browser schon vor P2-58 zwischengespeichert hat, kommen bis zum Ablauf ihrer Cache-Frist (bei älteren Berichten gut eine Woche) noch ohne Sandbox; Neuladen (Cmd+R) oder einmal den Browser-Cache leeren behebt das. Bestandsaufnahme und Messungen: Bau-Spec P2-58.

Netzwerk-Import: Listen aus einer Datei (P2-62)

Zielfirmen, Headhunter und Netzwerk-Kontakte lassen sich jederzeit aus einer Datei anlegen: Knopf „⇪ Aus Datei importieren“ in allen drei Reitern der Seite Netzwerk. Vorgaben vom 01.10.2026: CSV und Excel (.xlsx) mit Vorlage je Liste, dazu der LinkedIn-Export Connections.csv (nur Netzwerk-Kontakte); bestehende Einträge werden nur in leeren Feldern ergänzt und nie überschrieben, in der App gelöschte bleiben gelöscht. Das ist die Regel der früheren Einmal-Migration aus Excel (Phase 22, das Werkzeug ist entfernt; Prinzip 4 in §3: Dedup lebt von behaltenen Rows). Das Modul importiert kein internes Skript (ein Test hält das fest). Spec: P2-62.

Bausteine: app/netzwerk_import.py (der Kern, kennt kein FastAPI und wirft ImportFehler(status, text)), app/routes_netzwerk_import.py (Router mit Präfix /api: liest die Datei mit der Grenze von 5 MB, bevor geparst wird, und übersetzt ImportFehler in HTTPException; die Routen sind synchron und laufen im Threadpool, Parsen, Sicherung und Schreiben blockieren den Event-Loop also nicht), die Einbindung in main.py (include_router), die Oberfläche (s. unten) und tests/test_netzwerk_import.py. Der Kern bietet drei öffentliche Funktionen: vorlage(liste, format), vorschau(liste, dateiname, inhalt, *, session) und importieren(liste, dateiname, inhalt, *, session, daten_dir=None).

Endpunkte ({liste} ist zielfirmen, headhunter oder kontakte, sonst 404; Fehler kommen als {"detail": <Kundentext>}):

  • GET /api/netzwerk-import/{liste}/vorlage?format=csv (oder xlsx, ohne Angabe csv): die Vorlage zum Herunterladen (Content-Disposition: attachment, Dateiname Vorlage_Zielfirmen.csv, Vorlage_Headhunter.xlsx, Vorlage_Netzwerk-Kontakte.csv usw.). Sie enthält nur die Kopfzeile mit den deutschen Spaltennamen, die Pflichtspalte zuerst. CSV mit Semikolon und UTF-8 mit BOM (so zeigt Excel im deutschen Raum die Umlaute richtig); XLSX mit dem Blatt der Liste (Kopfzeile fett und fixiert) und einem zweiten Blatt „Hinweise“ (je Spalte Pflicht, erlaubte Werte und Formate, weitere erkannte Namen). Unbekanntes format: 422.
  • POST /api/netzwerk-import/{liste}/vorschau (Multipart-Feld datei): liest und plant, schreibt NICHTS (keine Datenbankänderung, keine Sicherung). Antwort: liste, format (csv, xlsx oder linkedin), blatt (nur bei Excel), spalten (erkannt mit spalte, feld, label; ignoriert), anzahl (zeilen, neu, ergaenzt, unveraendert, geloescht, fehler), zeilen (nr, aktion, anzeige, felder_ergaenzt, meldung), zeilen_gekuerzt und hinweise. nr ist die Zeilennummer in der Datei, die Kopfzeile mitgezählt. zeilen enthält alle Fehler- und Gelöscht-Zeilen plus die ersten 100 übrigen (ZEILEN_UEBRIGE) in Dateireihenfolge.
  • POST /api/netzwerk-import/{liste} (Multipart-Feld datei): plant neu (die Datei kommt noch einmal, der Server merkt sich nichts zwischen den Schritten), sichert und schreibt. Antwort: {"anzahl": {…wie bei der Vorschau…}, "sicherung": <Dateiname> oder null}.

Fehlercodes (Vorschau und Import): 413, wenn die Datei über 5 MB liegt (MAX_BYTES; der Router prüft UploadFile.size und liest höchstens 5 MB plus ein Byte, _einlesen prüft für Direktaufrufe noch einmal). 400 bei fehlender Datei im Feld, Endung außer .csv, .txt und .xlsx (.xls mit dem Hinweis, als .xlsx oder .csv zu speichern), leerer oder unlesbarer Datei (Binärdaten als CSV; kaputte Excel-Datei; entpackt über 200 MB, Schutz vor Zip-Bomben), fehlender Kopfzeile, fehlender Pflichtspalte (Liste.spalte_fehlt, etwa „Keine Spalte für die Firma gefunden. Erwartet wird zum Beispiel „Firma“.“) und mehr als 5.000 Datenzeilen (MAX_ZEILEN, ohne Kopfzeile und Leerzeilen). 404 bei unbekannter Liste. 409 nur beim Import: Es läuft gerade eine Sicherung, oder die Datenbank ist belegt. 422 bei unbekanntem format der Vorlage. 500, wenn die Sicherung scheitert („Die Sicherung vor dem Import ist fehlgeschlagen, es wurde nichts importiert. Grund: …“) oder das Schreiben scheitert („Der Import ist fehlgeschlagen, es wurde nichts importiert. Grund: …“); in beiden Fällen ist nichts geändert.

Konfiguration je Liste (LISTEN, EINE Tabelle statt Verzweigungen): Je Liste ein Liste (frozen dataclass) mit Modell, Feldern, Blattnamen, Schlüsselfeldern, Pflichtspalten und Pflichtwerten, Anzeige, Fehlertexten und Standardwerten für neue Einträge (standard_neu: bei Zielfirmen last_update = heute); je Feld ein Feld mit Vorlagenname, Synonymen, Hinweistext, Normalisierer (norm), in_vorlage, modellfeld und nicht_gleich. Aus dieser einen Tabelle entstehen im Backend die Spaltenerkennung, die Vorlagen (CSV und das Blatt „Hinweise“), die Planung und die Anzeige der Vorschau, eine zweite Liste, die auseinanderlaufen könnte, gibt es dort nicht. Hilfsfelder (modellfeld=False: Vorname, Nachname und die drei LinkedIn-Spalten) werden vor dem Planen aufgelöst und nie ins Modell geschrieben. Der Schlüssel ist derselbe wie bei den Anlege-Endpunkten in main.py (app.normalize.slug_parts): Zielfirma company, Headhunter firma und ansprechpartner, Kontakt name und unternehmen. Ein importierter und ein von Hand angelegter Eintrag können so nie nebeneinander stehen. Der Abgleich ist wörtlich nach slug_parts (klein, nur a-z0-9), ein unscharfer wie im Job-Ingest (Rechtsformzusätze, P2-39) findet nicht statt: „Muster“ und „Muster GmbH“ sind zwei Einträge.

Formate (_einlesen, geprüft wird in dieser Reihenfolge: Größe, Endung, leer):

  • CSV und TXT: UTF-8 mit oder ohne BOM, UTF-16 mit BOM (Excel „Unicode-Text“), sonst cp1252, im Notfall latin-1. Das Trennzeichen entscheidet _trennzeichen an der Kopfzeile: csv.Sniffer zählt nur, wenn sein Ergebnis dort mindestens so oft vorkommt wie jedes andere, sonst gilt das häufigste von ;, , und Tab (bei Gleichstand das Semikolon). Die Zeilennummer ist der laufende Datensatz, so zählt auch Excel.
  • XLSX (openpyxl, read_only=True, data_only=True): Die Blattwahl nimmt den ersten Namen aus Liste.blaetter (Zielfirmen: „Zielfirmen“, „Target Companies“; Headhunter: „Headhunter“, „Headhunters“; Kontakte: „Netzwerk“, „Netzwerk-Kontakte“, „Network Contacts“, „Kontakte“; verglichen über denselben Schlüssel wie die Spalten), sonst das erste Blatt, und hängt bei mehreren Blättern einen Hinweis an. Der Rang der Namen entscheidet, nicht die Reihenfolge in der Datei: Der Excel-Export der App hat vor „Netzwerk“ ein Blatt „Kontakte“ (die Stellen-Kontakte), das hier nicht gemeint ist. reset_dimensions() schützt vor Dateien mit falscher Dimensionsangabe (manche Programme schreiben „A1“ und schnitten sonst Zeilen ab). Kopfzeile ist die erste Zeile mit Inhalt.
  • LinkedIn (nur Liste kontakte, CSV oder .xlsx): Connections.csv hat Hinweiszeilen („Notes: …“) vor der Kopfzeile. Kopfzeile ist die erste Zeile mit „First Name“ und „Last Name“ unter den ersten 30 nicht leeren (_KOPF_SUCHE); als linkedin gilt die Datei, wenn zusätzlich „Connected On“ oder „URL“ in der Kopfzeile steht. Abgebildet werden Name (Vorname plus Nachname), Unternehmen („Company“), Rolle („Position“), Kanal „LinkedIn“ (nur bei leerer Kanalzelle) und Notizen aus „LinkedIn: <URL> · E-Mail: <Adresse> · verbunden seit TT.MM.JJJJ“ (nur, was vorhanden ist, _kontakt_aufloesen). Beziehung, letzter Kontakt, Priorität, nächste Aktion und Fälligkeit bleiben leer. Dazu kommt der Hinweis, dass LinkedIn alle Verbindungen liefert und die Liste für aktiv gepflegte Kontakte gedacht ist. Die Erkennung gilt auch für eine .xlsx (Abnahme: der Hinweis rät zum Kürzen in Excel, und Excel speichert dann oft als Arbeitsmappe; ein dabei in ein Datum verwandeltes „Connected On“ wird wie jede Datumszelle gelesen). Bei zielfirmen und headhunter ist eine LinkedIn-Datei eine gewöhnliche CSV; die Pflichtspalte fehlt dann, also 400.

Spaltenerkennung (_spalten_zuordnen): _schluessel() macht aus einer Überschrift den Vergleichsschlüssel (NFC, klein, ä/ö/ü/ß zu ae/oe/ue/ss, nur a-z0-9; NFC zuerst, weil ein „ü“ aus macOS-Dateien aus „u“ und Trema bestehen kann) und vergleicht ihn mit dem Vorlagennamen und den Synonymen der Felder. Die erste passende Spalte je Feld gewinnt, jede weitere für dasselbe Feld und jede ohne Zuordnung landet unter spalten.ignoriert. Pflicht ist mindestens eine der pflicht_spalten (Zielfirmen company; Headhunter firma oder ansprechpartner; Kontakte name, vorname oder nachname), sonst

  1. Ist die Namenszelle einer Zeile leer, ergibt sich name aus „Vorname Nachname“.

Werte: Zellen werden getrimmt (auch geschützte Leerzeichen und BOM), leer wird None, ganze Floats aus Excel verlieren das „.0“, Excel-Daten werden ISO. Daten bleiben ISO oder werden aus TT.MM.JJJJ, T.M.JJ (ab 2000) und LinkedIns „12 Sep 2023“ gelesen (_datum_iso; ein Tag, den es nicht gibt, ist nicht lesbar). Nicht lesbar: letzter_kontakt und last_update bleiben als Text stehen (_datum_text), next_action_date bleibt leer (_datum_streng), denn das Feld wird überwacht (fällige Aktionen erscheinen unter Follow-ups), und die Zeile bekommt eine Meldung. Angeglichen werden Priorität (Hoch, Mittel, Niedrig, auch englisch), der Kanal der Kontakte (LinkedIn, E-Mail, Telefon, Persönlich), Tier („1“, „1.0“ und „Tier 1“ ergeben „1“) und Szenario (Großbuchstabe, auch „a/b“); Unbekanntes bleibt, wie es ist. last_update einer Zielfirma ist der Dateiwert, bei NEUEN Einträgen ohne Wert heute (_heute(), eine eigene Funktion, damit ein Test das Datum festlegen kann).

Kein automatisches next_action_date: POST /api/network-contacts setzt ohne Angabe heute plus zehn Werktage. Der Import tut das bewusst nicht: Nach einem Import mit hunderten Zeilen stünden alle am selben Tag als fällige Aktion unter den Follow-ups. Die Gegenprobe (Automatik eingebaut) macht vier Fälle rot.

Plan (_planen, schreibt nichts): Je Datenzeile entstehen die Werte (_zeilenwerte), die Anzeige (_anzeige, „A · B“, höchstens 120 Zeichen) und die Pflichtprüfung (_pflicht_fehler): Der slug_parts eines Pflichtwerts darf nicht leer sein, sonst fehler; ein Wert, der nur aus Zeichen außerhalb von a-z0-9 besteht (etwa kyrillisch), bekommt eine eigene Meldung, weil slug_parts ihn zu einem leeren Schlüssel machte. Komplett leere Zeilen fallen still weg. Der Schlüssel wird gegen ALLE Zeilen der Tabelle (auch Tombstones) und gegen die Zeilen davor in derselben Datei gehalten: kein Eintrag ergibt neu, ein Tombstone geloescht (übersprungen, nie wiederbelebt), ein vorhandener Eintrag ergaenzt, wenn mindestens ein leeres Feld einen Dateiwert bekommt (_luecken, felder_ergaenzt nennt sie), sonst unveraendert. Ein gefüllter Wert wird nie überschrieben, eine leere Zelle löscht nichts. Eine zweite Zeile mit demselben Schlüssel wirkt auf das Ergebnis der ersten (Meldung „Doppelt in der Datei, siehe Zeile N“) und kann nur noch deren leere Felder füllen. Die Standardwerte für neue Einträge kommen erst am Ende, damit eine spätere Zeile desselben Eintrags den Wert noch liefern kann.

Karriereseiten-Regel (Feld.nicht_gleich): Der Excel-Export schreibt in die Spalte „Karriereseite“ ersatzweise die Webseite (karriere_url or website). Der Zielfirmen-Sweep lädt eine gesetzte karriere_url direkt (Cache) und sucht dann nicht mehr nach dem Karriere-Link auf der Webseite; er läse also die Startseite als Karriereseite. Eine Karriereseite, die der Webseite der vorhandenen Firma gleicht (_url_vergleich: ohne Schema, ohne „www.“, ohne Schrägstrich am Ende), ergänzt karriere_url deshalb nicht. Eine NEUE Firma behält beide Werte, wenn die Datei beide Spalten trägt. Die Gegenprobe ohne die Regel macht zwei Fälle rot.

Schreiben (importieren):

  1. Einlesen und erste Planung, nur lesend. Gibt es keinen Auftrag (neu + ergaenzt == 0), endet der Aufruf hier mit sicherung: null: keine Sicherung, kein Schreibzugriff.

Die Datenbank kommt aus dem Engine-Pfad der Session (session.get_bind().engine.url.database), der Datenordner aus daten_dir; so sichert ein Test genau die Datenbank, in die er schreibt. SicherungLaeuft ergibt 409, jeder andere Fehler 500, beide Male ist nichts geändert.
  3. BEGIN IMMEDIATE (_schreibtransaktion_beginnen): Schreibsperre ab hier. Ist die Datenbank belegt (SQLite meldet „locked“ oder „busy“ nach der Wartezeit von 15 Sekunden aus db.CONNECT_ARGS), ergibt das 409 statt eines hängenden Imports. Steht die Verbindung schon in einer Transaktion, bleibt es dabei.

  5. _schreiben: Eine Ergänzung setzt nur die geplanten Felder und updated_at. Neue Einträge entstehen mit dedup_key über flush_or_duplicate (SAVEPOINT je Zeile, session.add erst im Callback, s. dessen Docstring). Scheitert ein Auftrag an einer Dublette, weil ein gleichzeitiger Import denselben Schlüssel angelegt hat, wirkt er wie eine Ergänzung (wie bei der früheren Einmal-Migration), und die Zähler der Antwort werden umgebucht (neu minus eins, dafür ergaenzt, unveraendert oder geloescht plus eins). Dann session.commit().
  6. Jeder andere Fehler beim Schreiben ergibt rollback() und 500. Eine Logzeile [netzwerk-import] <liste>: <n> neu, <n> ergänzt, Sicherung <Datei> geht auf die Standardausgabe des Servers.

Warum BEGIN IMMEDIATE ausdrücklich: flush_or_duplicate allein ist unter pysqlite nicht atomar. pysqlite eröffnet nur vor INSERT, UPDATE und DELETE selbst eine Transaktion, nicht vor einem SAVEPOINT. Der SAVEPOINT startet sie, und sein RELEASE schließt sie wieder mit einem COMMIT. Ohne die ausdrückliche Transaktion bliebe nach einem Fehler mitten im Schreiben ein Teil der Zeilen stehen: Scheitert der Import bei der dritten Zeile, stünden die beiden ersten in der Datenbank (belegt in test_flush_or_duplicate_allein_ist_unter_pysqlite_nicht_atomar, das Verhalten im Import prüft test_eine_transaktion_fehler_mitten_im_schreiben_schreibt_nichts). Schlüge der erste Test einmal an, hat sich das Verhalten von Python oder SQLAlchemy geändert und die Vorkehrung ist überholt. Der Beginn mit Schreibsperre schließt außerdem die Lücke zwischen Planung und Schreiben. Gegenproben: Ohne BEGIN IMMEDIATE werden zwei Fälle rot, ohne expire_all() einer.

Drittanbieter-Lizenzen (P2-77)

Die Seite Rechtliches → „Drittanbieter-Lizenzen“ wird erzeugt und nicht von Hand gepflegt. Quelle sind die Lockfiles: backend/requirements-lock.txt (Python) und frontend/package-lock.json (npm). backend/pyproject.toml und frontend/package.json liefern nur die Einteilung in „direkt“ und „mitgebracht“. Der Generator pipeline/drittlizenzen.py schreibt zwei Dateien, beide werden nie von Hand geändert:

  • frontend/src/rechtliches/drittlizenzen.md: die Übersicht mit Paket, Version und Lizenzkennung, bei direkten Paketen mit Zweck. Dazu die Bauwerkzeuge als Zählung je Lizenz sowie die Listen der separat installierten Programme und der angebundenen Drittdienste.
  • frontend/src/rechtliches/drittlizenzen_texte.txt: der unveränderte Wortlaut aller mitgelieferten Lizenzen. Pakete mit wortgleichem Text stehen in einem Block. Erlaubt sind nur zwei Angleichungen: Zeilenenden auf LF und keine Leerzeichen am Zeilenende. Die Seite lädt die Datei erst auf Klick („Lizenztexte anzeigen“) als eigenen Chunk, das Haupt-Bundle bleibt klein.

Befehl (vom Projekt-Root, der Wrapper folgt dem Muster von scripts/docs_html.sh):

scripts/drittlizenzen.sh              # erzeugt beide Dateien
scripts/drittlizenzen.sh --pruefen    # vergleicht nur, schreibt nichts

Exit 0 = erzeugt bzw. aktuell, 1 = nur bei --pruefen: mindestens eine Datei ist veraltet (die Ausgabe nennt sie), 2 = Fehler, die Meldung nennt Paket und nächsten Schritt. Der Generator liest die Metadaten und Lizenzdateien aus dem venv und aus dem Build-Spiegel ~/.bewerbung_mgmt_node/frontend_build/node_modules (frontend/build.sh). Passt einer von beiden nicht zum Lockfile, bricht er mit Exit 2 ab und nennt den Befehl, der es behebt. Er läuft nur in der Entwicklung (AUSSCHLUESSE in pipeline/kundenpaket.py), die beiden erzeugten Dateien sind dagegen Pflichtdateien des Kundenpakets.

Wann: nach jeder Änderung an einem Lockfile oder an pyproject.toml bzw. package.json, vor dem Commit. Die Ausgabe ist deterministisch (kein Datum, keine Version, kein Pfad), zwei Läufe ergeben byte-gleiche Dateien.

Lizenzkennung, nie geraten: erst License-Expression, dann das Feld License, wenn es genau eine Kennung der Positivliste enthält, zuletzt die Tabelle LIZENZ_FESTGELEGT (Kennung plus die ersten zwölf Hex-Zeichen des SHA-256 des Lizenzwortlauts). Passt keine Stufe oder hat sich der Wortlaut geändert, bricht der Generator ab und nennt den Text, den man lesen muss.

Was die Wache prüft: tests/test_drittlizenzen.py läuft in der CI (backend und backend-windows) und braucht weder venv-Metadaten noch node_modules. Sie vergleicht den Bestand der Seite (Paketzeilen der Übersicht, Gilt für-Zeilen der Texte) mit den Lockfiles, prüft jede Kennung gegen die Positivliste und die Form beider Dateien (UTF-8, nur LF, genau ein Zeilenende am Schluss). Sie wird rot, sobald ein Lockfile sich ändert und die Seite nicht neu erzeugt wurde oder eine Lizenz außerhalb der Positivliste auftaucht.

Was sie nicht prüft: den Wortlaut. Das leistet nur --pruefen, und das läuft nur lokal (es braucht die installierte Umgebung), nicht in der CI. Ändert ein Paket bei gleicher Version seinen Lizenztext, fällt es nicht auf; veröffentlichte Versionen auf PyPI und npm sind unveränderlich, das Risiko ist klein. Ebenfalls offen: Die Texte stammen aus einer macOS-Installation, Pakete für Windows oder Linux können andere Lizenzdateien tragen. „Direkt“ und „mitgebracht“ folgen pyproject.toml und package.json, nicht den tatsächlichen Imports.

Pflege von Hand (alles in pipeline/drittlizenzen.py):

  • ZWECK: je direktes Paket ein kurzer Zweck. Ein neues direktes Paket ohne Eintrag bricht den Generator mit Exit 2 ab, die Meldung nennt das Paket.
  • LIZENZ_FESTGELEGT: nur für Pakete, deren Metadaten keine eindeutige Kennung nennen (heute google-auth, google-auth-oauthlib, pyasn1_modules). Den Lizenztext im *.dist-info lesen, die Kennung bestimmen, dann Kennung und Hash eintragen. Nicht ohne Hinsehen übernehmen.
  • PROGRAMME und DIENSTE: die Listen der separat installierten Programme und der angebundenen Dienste. Ändert sich eine Dienstanbindung, gehört auch datenschutz.md auf den Prüfstand.

Die Positivliste ist eine Entscheidung der Projektleitung (16.10.2026): MIT, MIT-0, ISC, BSD-2-Clause, BSD-3-Clause, Apache-2.0, PSF-2.0, MPL-2.0 (certifi) und OFL-1.1, nur für Bauwerkzeuge zusätzlich CC-BY-4.0. Bei einem Ausdruck gruppieren Klammern, AND bindet stärker als OR: A OR B ist erlaubt, wenn eine Seite erlaubt ist, A AND B nur, wenn beide es sind. Unbekannte Bestandteile (WITH, +) gelten als nicht erlaubt. Eine neue Lizenz macht die CI rot, und die Projektleitung entscheidet, ob sie auf die Liste kommt. Die Liste nicht ohne ihn erweitern.

Paketprüfung: Der Wortlaut enthält Autoren-Adressen und Firmennamen aus den Copyright-Zeilen und darf nicht verändert werden. Deshalb gilt für drittlizenzen_texte.txt eine pfadgebundene Ausnahme (_FREMDER_WORTLAUT, s. docs/RELEASE.md). Bauwerkzeuge erscheinen in der Übersicht ohne Wortlaut. Die Seite bleibt unter dem Hinweis „ENTWURFSFASSUNG“ und ist keine Rechtsberatung.

Tests & CI (backend/tests/, .github/workflows/ci.yml, Phase 57)

Aktuell mehr als 2000 pytest-Tests (Phase 57 startete mit 36) laufen isoliert von der Live-DB: conftest.py setzt BMS_DATA_DIR auf ein frisches tempfile.mkdtemp()-Verzeichnis ganz oben auf Modulebene — vor jedem Import von app.*/pipeline.*. Grund ist eine Import-Zeit-Falle: app/db.py bindet DATA_DIR/DB_PATH beim allerersten Modul-Import; würde irgendeine Testdatei ein App-Modul auf Modulebene importieren, bevor die Env-Variable gesetzt ist, bindet sich die gesamte Suite unumkehrbar an data/bewerbung.sqlite (Python cached Module, ein späterer Re-Import hilft nicht mehr). Deshalb importieren alle Testdateien App-Module ausschließlich funktionslokal in Fixtures/Tests, nie auf Modulebene — und ein Sicherheitsnetz in conftest.py bricht den Lauf hart ab, falls DB_PATH doch außerhalb des tmp-Verzeichnisses läge. Aus demselben Grund sind Fixtures (seed) bewusst rein synthetisch (Musterfirma GmbH, Test AG, erfundene Titel) — nie Zeilen aus der echten DB kopiert, sonst würde das Repo über die Tests personenbezogene Daten einschleusen (I2 aus Phase 56 gilt für Testdaten genauso).

Phase 79 schloss dieselbe Lücke für Artefakt-Pfade: mehrere Module (u. a. dedup_text, search_index, beirat_engine) lösten data/…-Pfade weiterhin gegen den Projekt-Root auf, während die Schreiber bereits gegen DATA_DIR schrieben — in Produktion identisch, unter Testisolation aber divergent (ältere Tests waren dort nur grün, weil sie vom selben Leck profitierten). Seither läuft jede Auflösung eines data/-Pfads über eine gemeinsame Funktion in app/db.py (folgt BMS_DATA_DIR); outputs/-Pfade bleiben bewusst gegen den Projekt-Root aufgelöst — die Dokumente des Nutzers sollen nicht isoliert werden.

CI (vier Jobs bei jedem Push nach main und jedem Pull Request: backend, backend-windows, frontend, secret-scan) führt diese Suite auf Python 3.12 aus, unter Linux und unter Windows. Der Pin folgt bewusst der lokalen venv-Realität, nicht umgekehrt. Bis Phase 57 war das Python 3.9 (seit Oktober 2025 EOL); Phase 58 hat das venv am selben Pfad mit identischem Lock (null Abweichungen) auf Python 3.12.13 aus Homebrew umgestellt — die EOL-Schuld ist damit beglichen. CI baut außerdem das Frontend gegen Node 24. PDF-Rendering (LibreOffice/soffice) ist dabei weiterhin eine offene Testlücke: weder lokal noch in CI durch skipif-Tests abgedeckt, kein stiller CI-Skip, sondern schlicht ungetestet — Kandidat für eine spätere Phase.

backend-windows (seit Phase 71D) führt dieselbe Suite auf windows-latest aus (working-directory: backend, python -m pytest tests -q); release.yml ruft ci.yml per workflow_call auf, ohne grünen Windows-Lauf entsteht also kein Release-Paket. Der Job secret-scan ersetzt das auf diesem Repo nicht verfügbare GitHub Secret Scanning (422, Plan-Limitierung) durch eine zweistufige Kette: lokal ein pre-commit-Hook (scripts/precommit_secret_scan.sh, reine Bordmittel git+grep, prüft nur staged Änderungen, <0,1 s), in CI gitleaks über die volle Commit-Historie (.gitleaks.toml). Wichtig für die Interpretation eines grünen Laufs: der secret-scan-Job bei einem Push prüft nur, ob im NEUEN Commit etwas gefunden wurde — die Action scannt bei diesem Trigger ausschließlich die neu gepushten Commits.
