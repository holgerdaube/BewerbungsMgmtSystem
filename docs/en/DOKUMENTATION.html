1. What is the system?

The BMS – Job Application Management System (BMS) is a local web app that brings the entire job search of one person together in one place: finding and scoring jobs, checking companies, producing application documents, preparing for and following up interviews, tracking email replies, maintaining the network and learning from all of it.

It is deliberately not an autonomous application robot but a human-in-the-loop tool: the system finds, scores and manages — the user decides. Nothing is sent without approval, no application is made without review, no facts are invented.

The central idea: Claude-in-the-Loop

Instead of external API keys and expensive services, the “intelligence” of the system is Claude itself. So-called skills (search, scoring, company check, CV tailoring, Gmail analysis …) are triggered by a plain-text sentence and write their results to the same central database that the web app reads from. There are two modes of operation:

  • Interactive — In a Claude session, the user says e.g. “Company check for job <no.>”, and Claude runs the skill.
  • Headless — the web app uses the agent runner to start the same skill as a background run (claude -p "<trigger sentence>"), e.g. via the “▶ Run” button on the job.

Both ways use exactly the same skills and write to the same DB — there is no second source of truth.

Two AIs: Claude or ChatGPT (P2-86)

Runs go either through Claude Code (claude -p, the default) or through OpenAI's Codex CLI (codex exec, ChatGPT, a preview in the first release). The choice is made in sucheinstellung.ki_anbieter (claude | chatgpt) via GET/PATCH /api/einstellungen and the “AI” card in Settings; the installation guides ask for it in step 0. GET /api/ki-status reports for each provider whether the program is installed and signed in, and never reads a key. Queue, chains, timeout and cancellation remain shared in agent_runner; app/ki_anbieter.py holds what differs:

  • Call and environment: codex_argv builds codex exec --json with the workspace-write sandbox, network on and the prompt via standard input. codex_prompt names the skill explicitly, codex_umgebung removes OPENAI_API_KEY, CODEX_API_KEY and the Claude variables: the machine's sign-in applies (codex login, the subscription), never a separately billed key. The program finds the BMS via CODEX_BIN or the PATH.
  • Skills: .claude/skills remains the only source. skills_spiegeln copies them before every run to .agents/skills (not versioned), where Codex looks. AGENTS.md in the project translates the tool names of the skills (WebSearch, WebFetch, Read, Write, Edit, Task); the skills themselves still use those of Claude Code.
  • Evaluation: CodexAuswertung turns the JSONL stream into the result that the runner knows from claude -p. It recognises a reached subscription limit and a missing sign-in from the error text (abo_limit, anmeldung).
  • PDF: LibreOffice aborts in the Codex sandbox. codex_umgebung therefore sets BMS_PDF_UEBER_SERVER, and cv_export has the server convert outside the sandbox (POST /api/intern/pdf, only Word files from the program and data folders).
  • Costs: Codex reports no costs in dollars, and tokens only at the end of the turn. Under ChatGPT, AgentTask.cost_usd stays 0, usage is recorded in AgentTask.tokens, and there is no budget limit per run. Protection comes from the run's timeout, the limits of the subscription and the daily limit for runs.
  • Models: The tiers opus, sonnet, haiku remain what is stored; CODEX_MODELL maps them to the Codex models (§8 “AI models”). Fable is never selectable.
  • Permissions: The hooks and approvals from automation/agent_settings.json and the path guard apply only to Claude Code. Under ChatGPT, the sandbox restricts writing to the project, the log folder (plus the data folder, if it is outside the project) and, for email runs, the credentials folder. It allows reading across the whole user folder, including ~/.bewerbung_mgmt_secrets: a run has no need to go there, but it is not prevented.

Outside iCloud this is not necessary.

3. Basic principles

These principles run through the whole system and explain many design decisions:

  1. Human-in-the-loop. Nothing irreversible happens without the user's approval. Emails are never sent, only created as a Gmail draft. No automatic applications (phase 15 “Auto-apply” was deliberately dropped).

  2. Anti-hallucination. Skills with a research component work with evidence and verbatim quotes. “Not available” instead of guessing. Decisions the system must not make (appointments, acceptances) are marked as [BITTE PRÜFEN: …] placeholders (“please check”).

  3. Four-eyes principle for job hits. Every job found must pass a verification gate before it may enter the DB: a mechanical URL checker (verify_jobs.py) plus a separate, adversarial review subagent confirm existence and currency. A mere free-text warning in the finding does not protect — only a gate that the ingest enforces. Trust matrix: Apify, mail alert and Nejo URLs are treated as authentic; URLs constructed by WebSearch need a canonical posting, otherwise they are not ingested.

  4. Dedup depends on retained rows. “Discarded → No match” remains in the DB as a tombstone, so that the same hit (same link) does not reappear as “New” the next day. The same logic applies when deleting jobs (soft delete, phase 32). Since P2-36 the ingest distinguishes: the same posting (same link), every further posting for a job that is still running, and hits in the bin remain blocked. A NEW posting of the same job (company + title, gender suffix ignored) for a job in a final status, however, appears as “New” again, with the note NEUAUSSCHREIBUNG? (“re-posting?”). Case A: A job “Head of Customer Success (m/w/d)” had been sorted out as No match; the new posting “(m/f/d)” came two weeks later and led to an application. A plain block would have silently discarded it. Since P2-39 the company name is additionally normalised for the comparison (legal-form and region suffixes such as GmbH/SE/Deutschland/EMEA removed), so that two spellings of the same company do not slip past two different company rows (measured on a real data set, 12.09.2026: 15 company groups collapse, 5 genuine job pairs now come together, 0 false alarms). Case B: Two spellings of the same company (“Beispiel” and “Beispiel GmbH”) — three jobs hung on two company rows for the same employer; every duplicate stage missed the match until the company spelling itself was normalised.

  5. Budget guardrails. Real money (Apify) has hard daily limits ($0.50/day, BudgetLimit table). The headless Claude runner runs on the Max subscription (virtual money), but has outlier brakes (per-run cap, tasks/day). Under ChatGPT there are no costs in dollars and no cap per run (Codex reports tokens only at the end of the turn); the brakes are timeout, subscription limit and tasks/day.

  6. Derived views instead of write triggers. Excel export, daily digest, full-text search index and, since phase 81, the coach site export can all be rebuilt completely (refresh_views.sh and coach_site.sh respectively), instead of being spread across ten write points. Their build state is visible (staleness is shown, not hidden). The Excel export itself now additionally shows the 0–100 CV match score, the reason for sorting out (from “Notes & history” instead of an empty column) and the Advisory Board rating as a coloured number (phase 75). Since P2-81 the “Applications” sheet shows, for each job applied for, the date found, the application date, the date of each interview round 1–6 (interview.scheduled_at, alternatively transcript.recorded_at) and the rejection date (earliest rejection email, alternatively the status change in the history, as a local calendar day).

  7. One activity log for everything. Every background activity — runner skill as well as in-server engine (Advisory Board) — writes its own AgentTask row (status, log, duration, cost). The Task Centre reads only this table and thus shows EVERYTHING automatically; no parallel bookkeeping (phase 42).

  8. Only for the applicant. The BMS supports only the side that is applying. Functions with which employers evaluate, sort or select applicants are not included: they would fall under the high-risk rules of the AI Regulation (AI Act, Annex III no. 4). Taken over from the former sales checklist when it was dropped on 29.10.2026.

5. The application workflow

A job moves through fixed statuses (Kanban on the Pipeline page):

Neu → Prüfen → Beworben → Interview → Angebot → (Zusage / Absage)
                                          ↘ Kein Match / Beirat abgelehnt / Nicht verfügbar / Geparkt

(In English: New → To review → Applied → Interview → Offer → (Acceptance / Rejected); No match / Rejected by board / Not available / Parked.)

The daily flow (daily run)

The daily run is the morning run and orchestrates serially:

  1. Job search (WebSearch + Nejo + Arbeitsagentur, optionally Apify) — three runs by bucket (Remote · Germany-wide · city + local area), new hits as “New” after the four-eyes check
  2. Mail job search — process job alert emails from the mailbox into jobs
  3. Target company sweep — check 12 career pages in rotation
  4. Headhunter search — check 15 headhunter pages in rotation (separate agent)
  5. Applied-jobs check (phase 74) — weekly availability check of all running applications (Applied/Interview): first the original URL, and if the portal is closed, the career page (phase 73 mechanism); a separate 7-day pre-check usually saves the run. Writes only availability status + check date — never changes the application status itself
  6. Email check — mailbox of the last 24–36 h, assigning replies to applications
  7. Views refresh — rebuild Excel export, daily digest, full-text search index
  8. Budget sync

The headless/automatic chain behind the daily run (agent_runner.RECIPES["tageslauf"]) inserts, after the email check, the rejection analysis once per calendar week (P2-79; pre-check without starting a model, a failure does not stop the chain, see docs/AUTOMATION.md) and additionally appends Update coach site (phase 81/82) as the last, deliberately non-fatal link — without complete configuration or with the switch turned off, the step ends green (exit 0); a real error after that marks only this one task, and the rest of the chain is left untouched.

Result: a compact morning summary (top hits, rotation states, applied-jobs check, Gmail, open/overdue actions).

Per job: the application package — mandatory core and optional components

(P2-41, 15.09.2026 — previously “four-step preparation”: the Advisory Board check was step 2 with a lock in front of cv-match, and the cover letter was always the last chain step. Both are now optional, without a lock, and run independently of the mandatory core.)

Mandatory core (sequential, real data dependency — company fit as context for the match, the draft from cv-match as the basis for cv-erstellen):

  1. Step 1 — firma-pruefen: company fit dashboard (business model, market, AI disruption, role influence, employer reality) + verbatim job posting snapshot. Both layouts are rendered deterministically from code (pipeline/company_fit.py/pipeline/posting_snapshot.py ::render_full(), phase 79) — the model now supplies only content, never HTML, so that the layout no longer drifts across runs. For a job whose portal is closed, the step determines the company's career page automatically (phase 73).
  2. Step 2 — cv-match → cv-erstellen: match dashboard with a weighted requirements table + tailored CV draft (DE/EN), directly editable on the job detail page. Rebuilds from the current base CV file on EVERY run (phase 78 — an earlier “already done” shortcut could leave a draft standing on an outdated structure). Then the button “Create CV” (cv-erstellen) → Word + PDF + ATS scan from the (possibly edited) draft. Now waits only for company fit (step 1) — no longer for the Advisory Board.

Optional components — own marker (○ open / ✓ done), no lock, neither for itself nor for any other step:

  • Check job (Advisory Board) (phase 40): the 7-member application Advisory Board checks the job description
  • CV according to the charter procedure — moderated live debate (3–5 members, followable on the job detail page via SSE)
  • vote of all 7 (6 weighted review areas), decision calculated deterministically → HTML dashboard with traffic light (🟢 Apply / 🟡 Conditional / 🔴 Do not apply), registered under “Files & documents”. On 🔴 the card offers the one-click status “Rejected by board” (phase 41) — the user decides. Stays at its logical position (triage BEFORE the CV effort), but continues to run in-server via beirat_engine.py, NOT as a chain link of the runner — stage 1 of the P2-41 decision; chaining is not built.
  • anschreiben-erstellen: truthful cover letter with direct address. Uses the tailored CV once the mandatory core has run — without a finished CV the skill falls back to the base CV, without company fit to the posting + its own research.

Application package (agent_runner.RECIPES["bewerbungspaket"]): ONE button starts the mandatory core; a tick box “with cover letter” appends the optional component to the chain (pre-set from the Settings card “Application package — default scope”, off by default). The former recipe deepdive is dropped without replacement — identical in content to the application package without a cover letter.

job-deepdive (interactive skill, not to be confused with the dropped recipe) does company fit + CV in one go. Afterwards, optionally: entscheider-recherche, interview-vorbereiten.

6. The skills (the “intelligence”)

24 skills, grouped by workflow phase. Triggered by a plain-text sentence (interactive) or a button (headless, where marked).

Search — finding new jobs (→ status “New”)

  • jobsuche — “search for new jobs” · WebSearch (default) + Nejo + Arbeitsagentur (German title synonyms) + optionally Apify, one run per bucket, hard limits (including only companies with 100+ employees, evidence rule), target-role fit 1–5, four-eyes, ingest. Headless-capable.
  • mail-jobsuche — “Mail job search” · job alert emails from Gmail → several postings per digest, dedup against the job search. Headless-capable.
  • zielfirmen-sweep — “Target company sweep” · 12 career pages in rotation out of the ~68 target companies.
  • headhunter-suche — “Headhunter search” · 15 headhunter pages in rotation; confidential assignments as [vertraulich] <Headhunter>. Separate agent.

Hard limits and score (P2-74). The same rule applies to all four search runs; it is set out in config/scoring_rubrik.md: a hard limit applies only with evidence from a posting, email or search result, never on an assumption. Hybrid outside the local area is not a relocation and belongs in the bucket “Germany-wide”. The score sorts, it does not filter out: whatever passes the limits is created with its score, even with 1 or 2. The final report names, for each job sorted out, the limit and the evidence. For mail-jobsuche the core of the rule is additionally in the runner's task template (agent_runner.PROMPTS), because that is where the drop was measured: after a model change, only 10 % instead of 44 % of the extracted postings reached the ingest.

Preparing an application (per job)

  • firma-pruefen (step 1) — company fit dashboard + posting snapshot (both rendered deterministically from code, phase 79/design review — the model supplies only content) → data/company_fit/, data/job_postings/. For a job whose portal is closed: automatic career page fallback (career_url/portal_closed, phase 73).
  • cv-match (step 2a) — match dashboard + tailored CV draft (editable), rebuilds on every run from the base CV instead of reusing an old draft (phase 78) → outputs/cv/.
  • cv-erstellen (step 2b) — from the (possibly edited) draft: Word/PDF + ATS scan. Since P2-45 the draft is also editable AFTER creation: expand the text window, change, save, “Recreate CV” — same record, same file, Word/PDF/ATS are produced anew. The page-break protection resets its “keep” properties on every run (P2-47) — otherwise flags accumulated over several runs until a whole position slid onto the following page as an indivisible block (methodology v2, phase 55: score = degree of optimisation over ONE 15-keyword list generated in cv-match, raw ratio separately visible, one-off feedback loop) → outputs/cv/. Base CVs are structured to be Workday/ATS-parser compatible (title directly before the company line, phase 76 — previously “Autofill with Resume” read title and position shifted by one position).
  • job-deepdive — both together. Claude-in-the-Loop.
  • entscheider-recherche — real functional decision-makers (VP/Head/C-level) + previous incumbent, public sources only → Contact rows.
  • anschreiben-erstellen — truthful, company-specific cover letter with direct address (DE/EN, docx + PDF) → outputs/anschreiben/, application status “Prepared”.
  • initiativ-bewerbung — hidden job market: network check → create speculative job → decision-maker → warm/headhunter/cold route.

Securing the posting text (P2-75). Background: A job from a job email received HTTP 429 (“too many requests”) from LinkedIn on capture. The base snapshot stayed without posting text (finding QUELLE_VERTRAUT); company check, CV match and CV creation ran through anyway and did not know the requirements of the job. What was measured was throttling per request, not a block (3 of 12, 3 of 11 and 9 of 18 LinkedIn retrievals in the most recent mail job searches, scattered across the run). The remedy has three parts; the snapshot remains the one place for the posting text, and no second structuring route is created. Spec: P2-75.

  • Retry (pipeline/verify_jobs.py). check_url() retries only on HTTP 429, with the pauses _PAUSEN_429 = (3, 8, 20) seconds; a Retry-After as whole seconds up to 30 replaces the respective pause. If it is still 429 after the fourth attempt, the finding is, as before, NICHT_PRUEFBAR (evidence “HTTP 429 after 4 attempts (rate limit)”). 403 (bot block), login wall, 404/410 and expired markers are not retried; waiting does not help there. The result carries versuche; wiederholen=False gives the earlier behaviour with exactly one attempt. The pauses run through the module function _schlafen so that tests can replace them. The batches (check, bestand) first fetch all addresses and retry only the blocked ones in up to three further rounds after the pauses _RUNDEN_PAUSEN = (5, 10, 20); the pauses per run thus remain at 35 s at most (measurement on 14.10.2026 with 24 addresses: 9 → 2 → 0 blocked in 58 s). The summary names wiederholt and rate_limit_offen. The four search skills therefore call verify_jobs check with a timeout of 300000 ms.
  • Catching up (pipeline/posting_snapshot.py). hat_anzeigentext(job) is a pure read function: true if the snapshot carries text (base card, block “Full text (unedited)”, full-text candidates of older snapshots or a green structured version). anzeigentext_sichern(job_id) returns vorhanden (no network retrieval), nachgeholt or fehlt with a reason in plain text. The snapshot is replaced only on finding OK with text (render_basis(job, text, hinweis=…), in place, plus a JobLog of kind auto); every other finding leaves the file byte-identical. 8. Operations, Automation & Security

Everyday operation

Starting and stopping (no auto-reload — restart after every backend change):

macOS Windows
Start start.command · start_lan.command (Wi-Fi) start_windows.bat
Stop Ctrl+C in the server window, otherwise stop.command Ctrl+C, otherwise stop_windows.bat

The stop scripts are for the case where the server window can no longer be reached (closed, started in the background, hung). They end the process on the server port (default 8000), first politely and after 10 s by force — but before that they check whether agent runs are active or queued, and ask for confirmation. Reason: skill runs hang off the server as child processes, and an Advisory Board debate runs inside the server itself; a restart aborts them. --force skips the confirmation; a different port works via PORT=8010 ./stop.command.

For script/terminal use without a double-click:

lsof -ti :8000 -sTCP:LISTEN | xargs -r kill; sleep 1
cd backend && nohup ~/.bewerbung_mgmt_venv/bin/python run_server.py > /tmp/bms_server.log 2>&1 & disown

Environment variables. .env.example lists the settings that may deviate from the default (server port and address, BMS_DATA_DIR, BMS_SECRETS_DIR, limits for agent runs). The program reads them only from the environment (os.environ); it does not load a .env file itself. The values must therefore be set in every shell that starts the server.

Backup & restore, manual via scripts/backup_db.sh (copy using SQLite's online backup API, consistent even with concurrent writes). The automatic backup is described below in the section "Backups".

scripts/backup_db.sh                    # Backup anlegen: data/backups/bewerbung_backup_<JJJJMMTT_HHMMSS>.sqlite
scripts/backup_db.sh --label vor_x       # mit Suffix, z. B. vor einer riskanten Operation
scripts/backup_db.sh --rotate            # + Rotations-Kandidaten auflisten (Dry-Run, löscht nichts)
scripts/backup_db.sh --rotate --apply    # + Kandidaten wirklich löschen (behält die neuesten 15)
scripts/backup_db.sh --rotate --apply --keep 20   # andere Aufbewahrungsmenge

To restore, there are wiederherstellen.command and wiederherstellen_windows.bat (section "Backups"); by hand it works like this: stop the server, copy the desired backup back (cp data/backups/<datei>.sqlite data/bewerbung.sqlite), check integrity (sqlite3 data/bewerbung.sqlite "PRAGMA integrity_check;" → ok), restart the server. Manual backups are never deleted automatically — rotation deletes only with an explicit --apply.

sqlite3 CLI against the RUNNING app (Phase 67F): The app sets an explicit busy_timeout (15 s, backend/app/db.py). The sqlite3 CLI does not know this value (separate process, separate connection) and has 0 by default — an ad-hoc query against data/bewerbung.sqlite while the server is running and writing can abort immediately with "database is locked". For a query against the running app, therefore prepend:

sqlite3 data/bewerbung.sqlite "PRAGMA busy_timeout=5000; SELECT ...;"

This is not needed for a restore (the server is deliberately stopped then).

Outbound check (scripts/outbound_check.py, Phase 66B) reads the agent task logs under ~/.bewerbung_mgmt_logs/ (read-only) and lists where headless skills actually opened outbound connections (curl/WebFetch), against a maintained list of expected destinations:

python3 scripts/outbound_check.py            # Kurzübersicht + auffällige Treffer
python3 scripts/outbound_check.py --all       # vollständige Host-Liste statt Top-20
python3 scripts/outbound_check.py --days 7    # nur die letzten 7 Tage

No automatism, no cron, no alerting — a tool that runs manually when needed. It is detection, not prevention (honest assessment: "What the skill allowlist achieves — and what it does not" below).

Update information from GitHub releases (P2-82)

New versions appear as a GitHub release of the public repo holgerdaube/BewerbungsMgmtSystem. Two places query it, both only at the user's request: the button "Nach Updates suchen" (Check for updates) in the app (contract A of the build spec P2-82) and the update tool scripts/bms_update.py (contract U). As long as the repo carries no published release, the button shows "No version has been published yet."

  • Repo and address are constants, not environment variables. GITHUB_REPO appears in exactly two places, in app/update_pruefen.py and in scripts/bms_update.py (the tool must not import anything from app); tests/test_update_pruefen.py keeps both identical. Plus GITHUB_API = "https://api.github.com". Anyone who could redirect the address could slip in a foreign package. Only tests replace the constants in the process, using a trial server on 127.0.0.1; no test contacts GitHub.
  • Only on request. There is no query at start-up, no background query and no reminder. The running app asks only on click, the tool only after a double-click on update.command/update_windows.bat, the installation guides only with their download command. The daily run and the skills never talk to GitHub. A path argument and --offline prevent any contact by the tool.
  • What GitHub sees. Anonymously, without token and without identifier: the IP address of the computer and the request itself, with User-Agent: BMS-Update (for the information query also Accept: application/vnd.github+json and X-GitHub-Api-Version: 2022-11-28). No version, no system name, no machine identifier, nothing from the database. This is stated next to the button ( "GitHub receives this computer's IP address."), before every search by the tool and in the tab "Datenschutz" (Privacy) (frontend/src/rechtliches/datenschutz.md). The publisher runs no server for the program and receives no data.
  • Button, backend. GET /api/version/neueste (app/routes_version.py, deliberately def instead of async, so that the blocking query runs in the thread pool) calls update_pruefen.neueste_version( installiert): a GET on {GITHUB_API}/repos/{GITHUB_REPO}/releases/latest with httpx, follow_redirects=False, certificate verification on, at most 10 seconds (ZEIT_S) and at most 1 MB of response. The computer's proxy settings apply. The endpoint stores nothing, has no cache and writes no IP address and no response content to the log. The response is always 200 and carries installiert, neueste (from tag_name of the form vX.Y.Z), neuer (comparison of the number tuples, 1.10.0 is newer than 1.9.0; if the installed version is unknown or 0.0.0, neuer is true), veroeffentlicht (date from published_at), seite (html_url, only if it starts with https://github.com/{GITHUB_REPO}/releases/, otherwise null), aenderungen (body of the release, at most 4000 characters, text only) and fehler. On an error a customer text is in fehler and all fields except installiert are null: "There is no connection to GitHub.", "GitHub is not responding in time.", "The connection to GitHub was interrupted.", "The secure connection to GitHub could not be verified.", "The response from GitHub is invalid.", on 404 "No version has been published yet." and on 403/429 "GitHub is currently limiting requests. Please try again in an hour." (without sign-in, 60 requests per hour and IP address apply).
  • Button, interface. VersionKarte in pages/Einstellungen.tsx shows the button "Check for updates" (during the query "Searching …" and disabled) with the note on the IP address below it. The result reads "Your BMS is up to date (version X).", or "Version X has been released (DD.MM.YYYY)." with the changes and the link "View on GitHub ↗" (target="_blank", rel="noopener noreferrer", only if seite is set), or the error text. aenderungenListe shows the changes as plain text: only "- " lines, backticks as <code>, no HTML. For a package installation, the instructions for installing follow below it (quit the BMS, double-click update.command or update_windows.bat, start the BMS; without internet, put the ZIP file in the Downloads folder), for a Git installation "Development installation: updates come via Git." The app never installs. Installing works only with the server stopped, via the tool (its step 5 checks this).
  • Tool, information. online_auskunft() queries the same address and checks the response strictly: version from tag_name without a leading v (form X.Y.Z, at most 9 digits per part); url is the browser_download_url of the asset BMS_<version>.zip and must read exactly https://github.com/ {GITHUB_REPO}/releases/download/v<version>/BMS_<version>.zip; groesse (size) lies between 1 and PAKET_MAX_BYTES (200 MB); sha256 comes from digest (form sha256:<64 hex>, calculated by GitHub on upload) and, if digest is missing, from the first string of the asset BMS_<version>.zip.sha256. If both are missing, nothing is installed ("The checksum for the latest version is missing. It will not be installed."). seite is html_url under the same conditions as above. The query follows no redirect. The two module-level functions are fixed as online_auskunft and online_laden.
  • Tool, download. online_laden(auskunft, ziel) downloads to data/updates/pakete/BMS_<Version>.zip.teil; the file name comes solely from the verified version number, never from a response header. At most groesse bytes are read; size and SHA-256 are checked against the information before renaming to .zip ("The downloaded package is incomplete or damaged."); a damaged package never appears under the final name. Other BMS_*.zip and *.teil files in the folder are deleted beforehand, a file that is already present and matches is not downloaded again, and a package downloaded with --pruefen stays in place. After that the tool checks the manifest as for any package (version 3, SHA-256 per file).
  • Redirect rule. When downloading, the tool follows at most UMLEITUNGEN_MAX = 3 redirects. Each only to https://, to the standard port, without credentials in the address, and only to github.com or a host whose name ends in .githubusercontent.com (_ziel_erlaubt); any other destination is an error to which no request is ever sent. GitHub in fact redirects the download to release-assets.githubusercontent.com. This also applies to the .sha256 asset.
  • Selection sequence. The offer wins if it is higher than the installed version (with --erzwingen equal is enough) and higher than the best candidate in "Downloads". Every error of the online search is a notice, not an abort: it continues with the candidate from "Downloads". Without a candidate: if GitHub has answered and offers nothing higher, it says "Your BMS is up to date (version …)" with exit 0. If GitHub could not be reached or was not asked, the tool aborts with "No update package found …", followed by the reason.
  • Network. The tool uses only the standard library (urllib.request with ssl.create_default_context()). Certificate verification is never switched off and is never repeated without verification after an error; the opener has no redirect handler; the computer's proxy settings apply. Time limits ZEIT_AUSKUNFT_S = 10 and ZEIT_LADEN_S = 120. The text of a server response is never displayed: every response is mapped to a fixed customer text. Source-code guards (tests/test_bms_update_github.py): no _create_unverified_context, no CERT_NONE, os.environ only for the known names, no imports outside the standard library.
  • Old installations. Installations up to 1.7.0 keep querying the former package service and never get 2.0.0 there. There is no bridge package: anyone with such an installation downloads 2.0.0 once as a ZIP file from the release page into the Downloads folder; after that the tool searches GitHub itself.

Honest limits: The trust anchor is the publisher's GitHub account. Anyone who takes it over can publish a release with foreign code; digest and manifest would then come from the same place. Protection is two-factor sign-in and releases only via release.yml. Possible later: proof of origin via a GitHub attestation (actions/attest-build-provenance) and its verification in the tool. The request limit of 60 requests per hour is enough for one button; behind a shared company exit it can become tight. The release notes come from CHANGELOG.md and are shown only as text; formatting other than "- " lines is lost.

What the skill allowlist achieves — and what it does not (Phase 66)

automation/agent_settings.json activates a permission list for headless skills (claude -p): only explicitly allowed tools/commands may run, everything else is automatically forbidden. An honest limit matters here (see build spec Phase 66, "The honest starting point"):

  • What it achieves: protection against accidents. A skill that would inadvertently trigger rm, git push or chmod is stopped before anything happens — demonstrated in the real run of 10.07.2026, when Artifact (publication to the outside) was correctly blocked.
  • What it does NOT achieve: no boundary against a targeted prompt injection. The skills process foreign text unattended (job postings, incoming emails, company websites); Bash(python:*) is deliberately left unrestricted, because the documented pattern for DB write access is a Python heredoc. A Python one-liner can do everything curl can, and more — blocking only curl would be theatre; the same exfiltration would work two lines later via Python. This list therefore reduces only the damage from a mistake, not the risk of deliberate circumvention.

What Phase 66 delivers instead (damage limitation, labelling, detection instead of a pretended security boundary):

  • 66A — damage radius: agent_runner._child_env(kind) passes on to each skill subprocess only the secrets from agent.env released for THAT kind (table SECRET_KEYS_BY_KIND, only mapping at present: jobsuche-apify → APIFY_TOKEN), instead of giving every key to every subprocess as before — with a loud message in the task log if a skill needs more after all. 9 of 22 headless kinds additionally get disallowed_tools (WebSearch/WebFetch blocked where the skill demonstrably does not use them).
  • 66B — labelling: agent_runner.HEADLESS_SUFFIX (appended to EVERY headless prompt) explicitly marks every foreign text loaded via WebFetch/WebSearch/curl/gmail_client as data material, not as an instruction, with the request to ignore embedded instructions and report them in the report — supplemented at the two most concrete embedding points (firma-pruefen/ SKILL.md job posting snapshot, email-check/SKILL.md email classification). This is hygiene, not a guarantee — a behavioural rule for the model, not a technical barrier.
  • 66B — detection: scripts/outbound_check.py reads the agent logs (read-only) and lists outbound destinations (curl/WebFetch) against a maintained list of expected hosts — no automatism, no cron, no alerting, a tool for a manual look when needed.

Expressly open (not part of Phase 66, only named here rather than defined away):

  • gmail.compose scope: technically allows the Google API more than drafts (also sending) — the only boundary is the missing code path in pipeline/gmail_client.py (no send function, no /send endpoint), not the technology. Since Phase 71F the same guarantee applies to the IMAP provider pipeline/imap_mail.py (drafts only via APPEND, no smtplib import in backend/pipeline/ — anchored as a negative guard in tests/test_kein_sendcodepfad.py). As long as a skill subprocess runs with free python/curl, this code path can in principle be bypassed.
  • Gmail access is file-based, not env-based: gmail_client.py reads gmail_credentials.json/ gmail_token.json directly from the secrets directory. _child_env(kind) (66A) therefore structurally CANNOT restrict this access — every skill subprocess runs as the signed-in user and can read the files like any other local program.
  • Options for this, without Phase 66 implementing them: gradually move skills from free Python heredocs to a narrow, verified interface (e.g. a CLI with a fixed, auditable set of commands instead of arbitrary code) — that would make Bash(python:*) restrictable in the first place, but it is a separate, large phase, not an extension of this list.

On an error after the replacement, the backup from the start is copied back. Undo without a switch of its own: the backup "vor Wiederherstellung" (before restore) appears in the list on the next call. Only the database is replaced; outputs/ and uploads remain. Why no button in the app: app/db.py binds the database at import time in a single engine without dispose/reinit; a swap while running would be risky. Both launchers and the script are in PFLICHTDATEIEN, the .command in _STARTDATEIEN_AUSFUEHRBAR (pipeline/kundenpaket.py).

Profile file: the "Identity and search strategy" form (P2-69)

Modules. pipeline/profil_datei.py (contract F: pure functions for splitting and assembling plus lesen() and schreiben(), no import from app) and app/routes_profil_identitaet.py (contract A, router like routes_sicherung.py, in main.py only import and include_router). Lossless splitting. The form changes only what it displays. Everything else stays byte for byte the same: unknown sections, unknown lines in known sections, Sprachen / CV-Fassungen, the empirical section, blank lines, line endings (LF or CRLF) and the file header. The only exception in the header: the title line # Kandidatenprofil: <Name> follows along if the name is changed in the form and the line carries exactly the previous name. Saving without a change in the form produces exactly the same file.

  • The file is split into the header (everything before the first line ##) and the sections. They are recognised by their heading text (trimmed, case-insensitive, "starts with"): Identität (field lines: name, positioning, location as "address", contact as email and phone, LinkedIn, current; further field lines as weitere with an editable value), Kurzprofil, Harte Rahmenbedingungen and Bekannte Skill-Gaps (each free text) and, from Zielrolle, only the line Zieltermin. Older lines such as level or industry stay untouched in the file; title, level and industry come from the search plans. All other sections stay unchanged; the API reports only their heading (unveraendert).
  • A field line is ^(\s*[-*]\s*)\*\*(.+?):\*\*[ \t]*(.*)$. When changing, only the value is replaced; indentation, bullet and key stay. A new field goes after the last field line of the section. An existing field with an empty value keeps its line; only for the optional fields positioning, LinkedIn and current is it removed. A new field with an empty value is not created.
  • Contact: when reading, the text is split at · or |; the first part with @ is the email, the rest (joined with ·) is the phone. What is written is E-Mail · Telefon, without a separator if there is only one value.
  • Free-text sections go to the form without the blank lines at the start and end. When writing, the previous number of blank lines before and after the body is kept; an unchanged text leaves the section byte-identical. New lines get the line ending that predominates in the file.
  • If the file is missing, lesen() returns vorhanden=False, empty values and the target date, and schreiben() creates the template (structure as in beispieldaten._profil_md_text(), with the sections Identität, Kurzprofil, Zielrolle, Harte Rahmenbedingungen, Sprachen / CV-Fassungen, Bekannte Skill-Gaps / Red Flags and Empirie). If a known section is missing from an existing file, schreiben() creates it only if the form supplies content, before the empirical section or otherwise at the end of the file.

Writing and checks. schreiben() replaces atomically (temp file in the same folder, os.replace, UTF-8). Beforehand a copy of the old file goes into the bin data/papierkorb/ (date prefix JJJJMMTT_ as with _freier_name); nothing is hard-deleted. A ValueError with customer text (formal "you" form) reports: name missing (required), line break in a single-line field, length over 300 characters (single-line) or 5000 (free text), a key in weitere or zielrolle that exists neither in the file nor among the standard keys, and a free-text line that begins with ## (it would create a new section). Non-blocking hinweise: the address has no comma or no postcode (the place line of the cover letters is built from Straße Nr, PLZ Ort), or the email has no @.

The response carries vorhanden, stand, identitaet (name, positionierung, anschrift, email, telefon, linkedin, aktuell, weitere), kurzprofil, zielrolle (list of schluessel and wert), rahmenbedingungen, skill_gaps, unveraendert and hinweise. stand is the SHA-256 of the file content, empty if the file is missing. No release for foreign websites (CORS, P2-55)

The backend sends no Access-Control-Allow-Origin header. A foreign website in the same browser therefore does not get to see the API's responses, and requests that need a preflight (JSON content, PATCH, DELETE) are not even sent by the browser. The app's own callers need no release: the interface comes from the same server, also in LAN mode at http://<name>.local:8000; the Vite dev server forwards /api via proxy; skills and scripts use curl or Python, to which CORS does not apply. Until P2-55, main.py contained a CORSMiddleware with allow_origins=["*"] and all methods: any website could read jobs, emails and profile, start AI runs and delete jobs, even a locally opened HTML file (Origin: null). Anyone who must release an origin enters it individually, never *, and adjusts tests/test_keine_cors_freigabe.py. What CORS never protected against has been caught since P2-57 by the origin check (next section): simple requests without a preflight (POST without content, as a form or upload) are still sent by the browser; only the response stays hidden from the foreign page.

Origin and host check (P2-57)

Before every route, the middleware _Herkunftspruefung in main.py checks two things; on a violation it answers with 403 and a message in detail.

Host (every request, including interface and assets): The server answers only under an IP address, localhost, a name ending in .local or a computer name without a dot. A foreign domain cannot fake these names via DNS rebinding: if it switches its DNS entry to 127.0.0.1 after loading, its page is the same origin for the browser and would read the API without any CORS release, in local as well as LAN mode. The addresses that start_lan.command displays always work. Further names (router name such as mac.fritz.box, Tailscale, reverse proxy) are released by the environment variable BMS_HOSTS, separated by comma or space: on the Mac in the terminal BMS_HOSTS=mac.fritz.box ./start_lan.command (with a double-click in Finder no environment variable arrives), on Windows set BMS_HOSTS=mac.fritz.box in the same command prompt before starting.

Origin (everything except GET, HEAD, OPTIONS): If the browser sends an Origin, host and port must match the Host header. The scheme does not count, and a missing port counts as the default port of the origin's scheme, so that a proxy with TLS in front works. Origin: null (locally opened HTML file, sandboxed iframe, since P2-58 every report) is blocked. Without an Origin (curl, skills, scripts, Python) the request passes. The only exception is http://localhost:5173, the Vite dev server via its proxy: only to host localhost (the proxy rewrites the host to that) and only with Sec-Fetch-Site: same-origin or without this header. Another project on port 5173 that addresses the server directly reports same-site; browsers send no Sec-Fetch-Site at all to a .local name or a LAN IP, hence the binding to localhost. Port 5173 is part of the exception: vite.config.ts sets strictPort, so that Vite aborts if the port is taken instead of silently moving to 5174 (every write access would then get 403).

Until P2-57, any website could blindly trigger 21 routes, including discard (every job to "No match"), replacing the base CV with overwrite, the ZIP import (run skills-sortieren), POST /api/sicherung and the connection tests for coach site and email. Behind a reverse proxy, the proxy must pass the host header through including the port (Caddy does this by itself, nginx needs proxy_set_header Host $http_host;), and its name belongs in BMS_HOSTS. Residual risk: anyone on the same network who forges mDNS or LLMNR responses can still redirect via a .local or dotless name; in LAN mode such a person has direct access anyway. Contract: tests/test_herkunftspruefung.py, with a guard over all operations from the OpenAPI schema. The licence check that sat inside this check (402) from P2-67 to 1.7.0 has been removed since P2-82 (section "Licence — removed").

Reports in the sandbox (P2-58)

HTML reports from /api/artifact and the daily digest (/api/digest) carry the header Content-Security-Policy: sandbox allow-scripts allow-popups allow-popups-to-escape-sandbox (_BERICHT_SANDBOX in main.py). This gives the browser its own opaque origin (null) for them instead of that of the API. A script in a report, for instance via a prompt injection from web content that an AI run has picked up, then no longer reaches the API: reading fails for lack of a CORS release (P2-55), writing at the origin check (Origin: null → 403, P2-57). Until P2-58, such a script ran in the origin of the API, read jobs, emails and profile and wrote past the check with a suitable origin; reproduced in the browser, a trial report discarded a job. In addition there is Cache-Control: no-cache (both in _BERICHT_KOPF): without it Chrome showed a previously opened report from the cache with the old headers, i.e. without sandbox.

Still allowed (measured in Chrome 154): scripts (71 older reports up to 08.08.2026 build their content by script), links in new tabs (these tabs are normal pages, hence allow-popups-to-escape-sandbox), links in the same tab, printing via the browser menu and the embedded favicon. No longer allowed, used by no report: forms, alert and confirm, window.print() from a script (would need allow-modals), localStorage, cookies, fonts or data via fetch from the BMS server (both need CORS). Anyone who builds something like that into a report needs a separate release; never allow-same-origin, it would cancel the protection. PDF, images, Word and downloads (download=true) remain without the header, as does the interface itself (index.html, /assets). A new HTML route sets _BERICHT_KOPF; a guard in tests/test_bericht_sandbox.py reports every HTMLResponse outside artifact, digest and (since P2-59) routes_doku.dokument, the documentation page (next section). Residual risks: an injected script can still send the content of its own report to the outside or redirect the page. Reports that the browser had already cached before P2-58 come without sandbox until their cache period expires (for older reports a good week); reloading (Cmd+R) or clearing the browser cache once fixes that. Inventory and measurements: build spec P2-58.

The core offers three public functions: vorlage(liste, format), vorschau(liste, dateiname, inhalt, *, session) and importieren(liste, dateiname, inhalt, *, session, daten_dir=None).

Endpoints ({liste} is zielfirmen, headhunter or kontakte, otherwise 404; errors come as {"detail": <customer text>}):

  • GET /api/netzwerk-import/{liste}/vorlage?format=csv (or xlsx, csv if not specified): the template for download (Content-Disposition: attachment, file name Vorlage_Zielfirmen.csv, Vorlage_Headhunter.xlsx, Vorlage_Netzwerk-Kontakte.csv etc.). It contains only the header row with the German column names, the required column first. CSV with semicolon and UTF-8 with BOM (so that Excel in German-speaking regions displays the umlauts correctly); XLSX with the sheet of the list (header row bold and frozen) and a second sheet "Hinweise" (notes) (per column: required or not, permitted values and formats, further recognised names). Unknown format: 422.
  • POST /api/netzwerk-import/{liste}/vorschau (multipart field datei): reads and plans, writes NOTHING (no database change, no backup). Response: liste, format (csv, xlsx or linkedin), blatt (Excel only), spalten (erkannt with spalte, feld, label; ignoriert), anzahl (zeilen, neu, ergaenzt, unveraendert, geloescht, fehler), zeilen (nr, aktion, anzeige, felder_ergaenzt, meldung), zeilen_gekuerzt and hinweise. nr is the row number in the file, counting the header row. zeilen contains all error and deleted rows plus the first 100 others (ZEILEN_UEBRIGE) in file order.
  • POST /api/netzwerk-import/{liste} (multipart field datei): plans again (the file comes once more; the server remembers nothing between the steps), backs up and writes. Response: {"anzahl": {…as for the preview…}, "sicherung": <file name> or null}.

Error codes (preview and import): 413 if the file is over 5 MB (MAX_BYTES; the router checks UploadFile.size and reads at most 5 MB plus one byte; _einlesen checks once more for direct calls). 400 for a missing file in the field, an extension other than .csv, .txt and .xlsx (.xls with the note to save as .xlsx or .csv), an empty or unreadable file (binary data as CSV; broken Excel file; over 200 MB when unpacked, protection against zip bombs), a missing header row, a missing required column (Liste.spalte_fehlt, e.g. "No column for the company found. For example, "Firma" is expected.") and more than 5,000 data rows (MAX_ZEILEN, excluding header row and blank rows). 404 for an unknown list. 409 only on import: a backup is currently running, or the database is busy. 422 for an unknown format of the template. 500 if the backup fails ("The backup before the import failed; nothing was imported. Reason: …") or writing fails ("The import failed; nothing was imported. Reason: …"); in both cases nothing is changed.

Configuration per list (LISTEN, ONE table instead of branches): one Liste (frozen dataclass) per list with model, fields, sheet names, key fields, required columns and required values, display, error texts and default values for new entries (standard_neu: for target companies last_update = today); one Feld per field with template name, synonyms, hint text, normaliser (norm), in_vorlage, modellfeld and nicht_gleich. The backend derives from this one table the column recognition, the templates (CSV and the sheet "Hinweise"), the planning and the display of the preview; there is no second list there that could drift apart. Helper fields (modellfeld=False: first name, last name and the three LinkedIn columns) are resolved before planning and never written to the model. The key is the same as for the create endpoints in main.py (app.normalize.slug_parts): target company company, headhunter firma and ansprechpartner, contact name and unternehmen. An imported entry and one created by hand can thus never stand side by side. The comparison is literal according to slug_parts (lower case, only a-z0-9); a fuzzy comparison as in the job ingest (legal-form suffixes, P2-39) does not take place: "Muster" and "Muster GmbH" are two entries.

Formats (_einlesen; checks are made in this order: size, extension, empty):

  • CSV and TXT: UTF-8 with or without BOM, UTF-16 with BOM (Excel "Unicode text"), otherwise cp1252, as a last resort latin-1. _trennzeichen decides the delimiter from the header row: csv.Sniffer counts only if its result occurs there at least as often as any other; otherwise the most frequent of ;, , and tab applies (semicolon in a tie). The row number is the running record, which is how Excel counts too.
  • XLSX (openpyxl, read_only=True, data_only=True): sheet selection takes the first name from Liste.blaetter (target companies: "Zielfirmen", "Target Companies"; headhunters: "Headhunter", "Headhunters"; contacts: "Netzwerk", "Netzwerk-Kontakte", "Network Contacts", "Kontakte"; compared via the same key as the columns), otherwise the first sheet, and adds a note if there are several sheets. The rank of the names decides, not the order in the file: the app's Excel export has a sheet "Kontakte" before "Netzwerk" (the job contacts), which is not meant here. reset_dimensions() protects against files with an incorrect dimension entry (some programs write "A1" and would otherwise cut off rows). The header row is the first row with content.
  • LinkedIn (list kontakte only, CSV or .xlsx): Connections.csv has note lines ("Notes: …") before the header row. The header row is the first row with "First Name" and "Last Name" among the first 30 non-empty rows (_KOPF_SUCHE); the file counts as linkedin if, in addition, "Connected On" or "URL" is in the header row. What is mapped: name (first name plus last name), company ("Company"), role ("Position"), channel "LinkedIn" (only if the channel cell is empty) and notes from "LinkedIn: <URL> · E-Mail: <address> · verbunden seit TT.MM.JJJJ" (connected since DD.MM.YYYY) (only what is present, _kontakt_aufloesen). Relationship, last contact, priority, next action and due date stay empty. In addition there is the note that LinkedIn supplies all connections and that the list is intended for actively maintained contacts. The recognition also applies to an .xlsx (acceptance: the note advises trimming in Excel, and Excel then often saves as a workbook; a "Connected On" converted into a date in the process is read like any date cell). For zielfirmen and headhunter, a LinkedIn file is an ordinary CSV; the required column is then missing, hence 400.

Column recognition (_spalten_zuordnen): _schluessel() turns a heading into the comparison key (NFC, lower case, ä/ö/ü/ß to ae/oe/ue/ss, only a-z0-9; NFC first, because a "ü" from macOS files can consist of "u" and a diaeresis) and compares it with the template name and the synonyms of the fields. The first matching column per field wins; every further one for the same field and every one without a mapping ends up under spalten.ignoriert. At least one of the pflicht_spalten is required (target companies company; headhunters firma or ansprechpartner; contacts name, vorname or nachname), otherwise

  1. If the name cell of a row is empty, name is derived from "first name last name".

Values: Cells are trimmed (also non-breaking spaces and BOM), empty becomes None, whole floats from Excel lose the ".0", Excel dates become ISO. Dates stay ISO or are read from TT.MM.JJJJ, T.M.JJ (from 2000) and LinkedIn's "12 Sep 2023" (_datum_iso; a day that does not exist is not readable). If not readable: letzter_kontakt and last_update stay as text (_datum_text), next_action_date stays empty (_datum_streng), because the field is monitored (due actions appear under follow-ups), and the row gets a message. What is harmonised: priority (Hoch, Mittel, Niedrig — high, medium, low — also in English), the channel of the contacts (LinkedIn, E-Mail, Telefon, Persönlich — in person), tier ("1", "1.0" and "Tier 1" result in "1") and scenario (capital letter, also "a/b"); anything unknown stays as it is. last_update of a target company is the file value; for NEW entries without a value it is today (_heute(), a separate function so that a test can fix the date).

No automatic next_action_date: POST /api/network-contacts sets today plus ten working days if nothing is specified. The import deliberately does not: after an import with hundreds of rows, all of them would be due on the same day as an action under follow-ups. The counter-test (automation built in) turns four cases red.

Plan (_planen, writes nothing): For each data row, the values (_zeilenwerte), the display (_anzeige, "A · B", at most 120 characters) and the required-value check (_pflicht_fehler) are created: the slug_parts of a required value must not be empty, otherwise fehler; a value consisting only of characters outside a-z0-9 (for instance Cyrillic) gets a message of its own, because slug_parts would turn it into an empty key. Completely empty rows are silently dropped. The key is checked against ALL rows of the table (including tombstones) and against the rows before it in the same file: no entry results in neu (new), a tombstone in geloescht (deleted; skipped, never revived), an existing entry in ergaenzt (supplemented) if at least one empty field gets a file value (_luecken, felder_ergaenzt names them), otherwise unveraendert (unchanged). A filled value is never overwritten, an empty cell deletes nothing. A second row with the same key acts on the result of the first (message "Duplicate in the file, see row N") and can only fill its empty fields. The default values for new entries come only at the end, so that a later row for the same entry can still supply the value.

Career-page rule (Feld.nicht_gleich): The Excel export writes the website into the column "Karriereseite" (career page) as a substitute (karriere_url or website). The target-company sweep loads a set karriere_url directly (cache) and then no longer searches for the career link on the website; it would read the home page as the career page. A career page that equals the website of the existing company (_url_vergleich: without scheme, without "www.", without trailing slash) therefore does not supplement karriere_url. A NEW company keeps both values if the file carries both columns. The counter-test without the rule turns two cases red.

Writing (importieren):

  1. Read and first planning, read-only. If there is no job (neu + ergaenzt == 0), the call ends here with sicherung: null: no backup, no write access.
  2. Backup via app.sicherung.anlegen(), i.e. in the series of automatic backups under data/backups/auto. The database comes from the engine path of the session (session.get_bind().engine.url.database), the data folder from daten_dir; this way a test backs up exactly the database it writes to. SicherungLaeuft results in 409, any other error in 500; in both cases nothing is changed.
  3. BEGIN IMMEDIATE (_schreibtransaktion_beginnen): write lock from here. If the database is busy (SQLite reports "locked" or "busy" after the wait of 15 seconds from db.CONNECT_ARGS), this results in 409 instead of a hanging import. If the connection is already in a transaction, it stays that way.
  4. session.expire_all() and second planning under the lock, so that the state written is the state planned: the backup lies between the first planning and the writing, and in that time another process may have filled the same field. The response counts from this second planning.
  5. _schreiben: a supplement sets only the planned fields and updated_at. New entries are created with dedup_key via flush_or_duplicate (SAVEPOINT per row, session.add only in the callback, see its docstring). If a job fails because of a duplicate, because a concurrent import has created the same key, it acts like a supplement (as in the earlier one-off migration), and the counters of the response are rebooked (neu minus one, ergaenzt, unveraendert or geloescht plus one). Then session.commit().
  6. Any other error while writing results in rollback() and 500. A log line [netzwerk-import] <liste>: <n> neu, <n> ergänzt, Sicherung <Datei> goes to the server's standard output.

Why BEGIN IMMEDIATE explicitly: flush_or_duplicate alone is not atomic under pysqlite. pysqlite opens a transaction itself only before INSERT, UPDATE and DELETE, not before a SAVEPOINT. The SAVEPOINT starts one, and its RELEASE closes it again with a COMMIT. Without the explicit transaction, after an error in the middle of writing some of the rows would remain: if the import fails at the third row, the first two would be in the database (demonstrated in test_flush_or_duplicate_allein_ist_unter_pysqlite_nicht_atomar; the behaviour in the import is tested by test_eine_transaktion_fehler_mitten_im_schreiben_schreibt_nichts). If the first test ever fails, the behaviour of Python or SQLAlchemy has changed and the safeguard is obsolete. Starting with a write lock also closes the gap between planning and writing. Counter-tests: without BEGIN IMMEDIATE two cases turn red, without expire_all() one.

Interface (frontend/src/components/NetzwerkImport.tsx): Two building blocks, because the button belongs in the header row of the tab and the panel opens below it, as with TargetNew and NcNew: NetzwerkImportKnopf (secondary button with a border instead of a cyan fill, to the left of the create button) and the panel NetzwerkImport (props liste, onImportiert, onClose). pages/Netzwerk.tsx holds only the on/off switch (showImport; 12 lines inserted and none changed, so that merging with the changes of P2-61 to the same file stayed easy): in Netzwerk for the tabs target companies and headhunters, with an effect that closes the panel when the tab is switched, and in NetzwerkKontakte for the third. onImportiert reloads the page's list (loadRows or load). Sequence in the panel: choose file, POST …/vorschau, preview (recognised columns as chips, "column → field" if the heading differs; unused columns; five counters; notes; table of the rows with errors and deleted rows first), "Import (12 new, 3 to supplement)" (disabled when neu + ergaenzt == 0), POST … with the same file, result line "✓ 12 created, 3 supplemented. Backed up beforehand: <file>" and "Close". Uploads use fetch and FormData, not api(): that sets the JSON header, which multipart cannot tolerate (pattern Profil.tsx). Three safeguards: against double-click (schreibt), against the response of an outdated preview (lauf) and against reporting after a tab switch in the middle of the import (aktiv; the reload would otherwise hang on the tab of that time and write its rows into the new one). A TypeError from fetch means that the server is not responding or that the file was changed after selection (typical: corrected in Excel); the error text says both. Accessibility: an always-present live region (role="status") announces "File is being checked", "Preview ready …" and the result, the table has a caption, and the badges always carry plain text (colour is never the only carrier; errors: red with white, 4.58:1). The display names in "Supplemented: …" come from the labels of the recognised columns (spalten.erkannt); the list FELD_NAMEN in the component catches only fields that the server derives rather than reads from a column (for the LinkedIn export, channel and notes); it is the only second list of the import fields. Types in api.ts: NetzwerkImportVorschau, NetzwerkImportErgebnis, plus NetzwerkImportAnzahl, NetzwerkImportZeile, NetzwerkImportListe and NetzwerkImportAktion.

Third-party licences (P2-77)

The Legal → "Third-party licences" page is generated, not maintained by hand. The source is the lock files: backend/requirements-lock.txt (Python) and frontend/package-lock.json (npm). backend/pyproject.toml and frontend/package.json supply only the division into "direct" and "bundled" (transitive). The generator pipeline/drittlizenzen.py writes two files, neither of which is ever changed by hand:

  • frontend/src/rechtliches/drittlizenzen.md: the overview with package, version and licence identifier, with purpose for direct packages. In addition the build tools as a count per licence, as well as the lists of the separately installed programs and the connected third-party services.
  • frontend/src/rechtliches/drittlizenzen_texte.txt: the unchanged wording of all shipped licences. Packages with identical text are in one block. Only two adjustments are permitted: line endings to LF and no trailing spaces at the end of lines. The page loads the file only on click ("Show licence texts") as a chunk of its own; the main bundle stays small.

Command (from the project root; the wrapper follows the pattern of scripts/docs_html.sh):

scripts/drittlizenzen.sh              # erzeugt beide Dateien
scripts/drittlizenzen.sh --pruefen    # vergleicht nur, schreibt nichts

Exit 0 = generated or up to date, 1 = only with --pruefen: at least one file is out of date (the output names it), 2 = error, the message names the package and next step. The generator reads the metadata and licence files from the venv and from the build mirror ~/.bewerbung_mgmt_node/frontend_build/node_modules (frontend/build.sh). If either of the two does not match the lock file, it aborts with exit 2 and names the command that fixes it. It runs only in development (AUSSCHLUESSE in pipeline/kundenpaket.py); the two generated files, in contrast, are mandatory files of the customer package.

When: after every change to a lock file or to pyproject.toml or package.json, before the commit. The output is deterministic (no date, no version, no path); two runs produce byte-identical files.

Licence identifier, never guessed: first License-Expression, then the field License if it contains exactly one identifier from the allowlist, finally the table LIZENZ_FESTGELEGT (identifier plus the first twelve hex characters of the SHA-256 of the licence wording). If no stage matches or the wording has changed, the generator aborts and names the text that has to be read.

What the guard checks: tests/test_drittlizenzen.py runs in CI (backend and backend-windows) and needs neither venv metadata nor node_modules. It compares the contents of the page (package lines of the overview, Gilt für lines of the texts) with the lock files, and checks every identifier against the allowlist and the form of both files (UTF-8, LF only, exactly one line ending at the end). It turns red as soon as a lock file changes and the page was not regenerated, or a licence outside the allowlist appears.

What it does not check: the wording. Only --pruefen does that, and it runs only locally (it needs the installed environment), not in CI. If a package changes its licence text at the same version, it goes unnoticed; published versions on PyPI and npm are immutable, so the risk is small. Also open: the texts come from a macOS installation; packages for Windows or Linux may carry other licence files. "Direct" and "bundled" follow pyproject.toml and package.json, not the actual imports.

Maintenance by hand (all in pipeline/drittlizenzen.py):

  • ZWECK: a short purpose per direct package. A new direct package without an entry makes the generator abort with exit 2; the message names the package.
  • LIZENZ_FESTGELEGT: only for packages whose metadata name no unambiguous identifier (currently google-auth, google-auth-oauthlib, pyasn1_modules). Read the licence text in *.dist-info, determine the identifier, then enter identifier and hash. Do not adopt it without looking.
  • PROGRAMME and DIENSTE: the lists of separately installed programs and connected services. If a service connection changes, datenschutz.md also needs to be reviewed.

Report self-check (pipeline/report_check.py, 23.07.2026)

The generated HTML reports (ATS scan, match, company fit, Advisory Board check, transcript report …) are self-contained files: assets/report_theme_bms.html is not linked, so its CSS is copied into the <style> block of every report. If an LLM run shortens the CSS in the process, the markup stays correct, but the presentation breaks silently — this is exactly how an ATS scan lost its green/red keyword chips on 23.07. (class="chip pos" 9 times in the markup, .chip.pos missing from the <style>); it was noticed only in the browser.

The check is the countermeasure: deterministic, free, without prior knowledge of report types.

The same pattern with the app icon (P2-44, 23.09.2026): The template carries the icon as a 3.3 KB data URI, which every report copies along. In 37 of 2,701 files this string was mangled or replaced by a foreign icon — and stayed that way, because app/favicon.py left every file alone that carried any icon. Since then the app icon wins: a foreign icon link is replaced, multiple ones are reduced to one (apple-touch-icon remains untouched). All three levels — generator, /api/artifact on delivery and pipeline.favicon_nachruesten in the daily run — therefore also heal a wrong icon, not just a missing one. It compares used class combinations against existing CSS rules and reports every class that remains without effect. Since P2-72 no model writes CSS any more: the skill writes the report without <style>, bericht_stil einsetzen inserts the complete CSS, and the check runs directly afterwards. Both steps appear as one line in all six skills whose reports a model writes (job-deepdive, cv-match, cv-erstellen, interview-vorbereiten, absagen-analyse, angebot-vergleich). If either of the two reports a class without a rule, the model replaces the class with one from the template.

cd backend && ~/.bewerbung_mgmt_venv/bin/python -m pipeline.report_check ../data/company_fit/*.html

Exit code 0 = clean, 1 = at least one rule is missing. Repair is cheap (bericht_stil einsetzen inserts the complete CSS); an expensive re-run of the skill is never necessary for this. On the first run over the whole stock (289 reports) it found, besides this case, two old transcript reports with ineffective .signal/.amber classes; since then the stock has been completely green.

⚠️ Two deliberate exclusions, otherwise false alarms arise: JS template literals (class="${badgeClass(...)}" in company-fit reports) and foreign markup in the job posting snapshots (data/job_postings/ contains the copied original HTML including the company site's Tailwind classes) are skipped.

Tests & CI (backend/tests/, .github/workflows/ci.yml, Phase 57)

Currently more than 2,000 pytest tests (Phase 57 started with 36) run isolated from the live DB: conftest.py sets BMS_DATA_DIR to a fresh tempfile.mkdtemp() directory at the very top of module level — before any import of app.*/pipeline.*. The reason is an import-time trap: app/db.py binds DATA_DIR/DB_PATH at the very first module import; if any test file imported an app module at module level before the env variable is set, the whole suite would irreversibly bind to data/bewerbung.sqlite (Python caches modules, a later re-import no longer helps). All test files therefore import app modules only locally within functions, in fixtures/tests, never at module level — and a safety net in conftest.py aborts the run hard if DB_PATH should nevertheless lie outside the tmp directory. For the same reason fixtures (seed) are deliberately purely synthetic (Musterfirma GmbH, Test AG, invented titles) — never rows copied from the real DB, otherwise the repo would smuggle personal data in via the tests (I2 from Phase 56 applies to test data just as much).

Phase 79 closed the same gap for artefact paths: several modules (including dedup_text, search_index, beirat_engine) still resolved data/… paths against the project root, while the writers already wrote against DATA_DIR — identical in production, but under test isolation divergent (older tests were green there only because they benefited from the same leak). Since then every resolution of a data/ path goes through a shared function in app/db.py (which follows BMS_DATA_DIR); outputs/ paths are deliberately still resolved against the project root — the user's documents are not meant to be isolated.

CI (four jobs on every push to main and every pull request: backend, backend-windows, frontend, secret-scan) runs this suite on Python 3.12, on Linux and on Windows. The pin deliberately follows the local venv reality, not the other way round. Until Phase 57 that was Python 3.9 (EOL since October 2025); Phase 58 switched the venv at the same path with an identical lock (zero deviations) to Python 3.12.13 from Homebrew — the EOL debt is thereby settled. CI also builds the frontend against Node 24. PDF rendering (LibreOffice/soffice) remains an open test gap: covered neither locally nor in CI by skipif tests, not a silent CI skip but simply untested — a candidate for a later phase.

backend-windows (since Phase 71D) runs the same suite on windows-latest (working-directory: backend, python -m pytest tests -q); release.yml calls ci.yml via workflow_call, so without a green Windows run no release package is created. Tests that require POSIX carry @pytest.mark.skipif(os.name == "nt", …) and are skipped there: test_prozess_tracking.py (whole module: real sleep process groups, ps/os.killpg), test_beirat_stderr_deadlock.py (whole module: stub via chmod +x, starts without an interpreter via the shebang line), one test in test_cv_export.py (timeout kill via os.killpg), two permission asserts in test_log_pfade.py (st_mode == 0o600/0o700) and one test in test_tmp_aufraeumen.py (symlinks need special rights under Windows). No LibreOffice is installed on the Windows runner, so the Windows path of PDF generation never ran there. The customer's view of these limits is in docs/SETUP-WINDOWS.md (known limits, support matrix), the developer route under Windows in docs/INSTALLATION.md part 1. .gitattributes keeps text files on LF (otherwise test_docs_html.py would fail on Windows runners) and .bat/.cmd on CRLF.

Running tests locally. scripts/test.sh calls pytest in the venv against backend/tests/ (install once with ~/.bewerbung_mgmt_venv/bin/pip install -r backend/requirements-dev.txt). Isolation from the live DB works via BMS_DATA_DIR: conftest.py sets it itself to a fresh tmp directory before any app module is imported. data/bewerbung.sqlite stays untouched; the server on port 8000 can keep running in parallel.

Secret-guard hook (once per clone): scripts/install_hooks.sh writes a wrapper to $(git rev-parse --git-dir)/hooks/pre-commit (hooks are not versioned; this script is the reproducible way to get there) which, before every commit, checks the staged changes against a few token patterns (<0.1 s) and blocks on a hit. Deliberate exception: git commit --no-verify.

Rebuilding the Python environment. If the venv breaks (typical symptom after a brew upgrade/cleanup of python@3.12: bad interpreter), rebuilding from the lock helps:

The secret-scan job replaces GitHub Secret Scanning, which is not available on this repo (422, plan limitation), with a two-stage chain: locally a pre-commit hook (scripts/precommit_secret_scan.sh, plain built-in tools git+grep, checks only staged changes, <0.1 s), in CI gitleaks over the full commit history (.gitleaks.toml). Important for interpreting a green run: the secret-scan job on a push checks only whether anything was found in the NEW commit — with this trigger the action scans only the newly pushed commits.
